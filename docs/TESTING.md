# استراتژیِ تست — هرم، مرزها، و آنچه عمداً سنجیده نمی‌شود

> ⚠️ این سند **تصمیم‌ها** را می‌نویسد، نه فهرستِ تست‌ها را. فهرست خودش در
> کد است و کهنه نمی‌شود؛ سندی که تست‌ها را بشمارد، همان هفته کهنه می‌شود.

---

## هرمِ واقعی — اندازه‌گیری‌شده، نه آرزو

| لایه                    | فایل | تست       | چه چیزی را می‌سنجد                |
| ----------------------- | ---- | --------- | --------------------------------- |
| واحد (`tests/Unit`)     | ۵    | ۲۸        | منطقِ خالص، بدونِ دیتابیس         |
| ویژگی (`tests/Feature`) | ۱۱۰  | **۱٬۵۹۷** | درخواستِ کامل، از مسیر تا دیتابیس |
| فرانت (`tests/js`)      | ۵۵   | ۵۳۵       | کامپوننت، فرم، منطقِ مرورگر       |
| سرتاسری (`tests/e2e`)   | ۵    | ۱۳۹       | مرورگرِ واقعی، مسیرهای حیاتی      |

> ⚠️ اندازه‌گیری‌شده پس از فاز ۱۰ِ مرحلهٔ پنجم (کامیتِ `a5f7d4e`). عددِ
> سرتاسری شمارِ اجرا روی همهٔ نمایه‌های مرورگر است، نه شمارِ سناریو.

🔴 **این هرم وارونه است و باید صریح گفته شود.**

۱٬۵۹۷ تستِ ویژگی در برابرِ ۲۸ تستِ واحد یعنی بیشترِ منطقِ کسب‌وکار از
راهِ HTTP سنجیده می‌شود: هر ادعا یک مهاجرت، یک تراکنش و یک چرخهٔ کاملِ
درخواست هزینه دارد.

⚠️ هزینه‌اش عدد دارد: تست‌های جریمه در لایهٔ واحد **۲۵ میلی‌ثانیه** برای
۹ ادعا می‌گیرند؛ همان ادعاها از راهِ HTTP چند صد میلی‌ثانیه می‌شدند.

### ⚠️ ولی این را «بدهی» ننامیم بی‌آنکه دلیلش را بگوییم

بخشِ بزرگی از این پروژه **ذاتاً** یکپارچه است: چندمستأجری، مجوز،
تراکنش، قفلِ ردیفی، و مهاجرت. تستِ واحد برای `ComplexScope` معنی ندارد —
چیزی که باید ثابت شود این است که کوئریِ واقعی روی دیتابیسِ واقعی داده‌ی
مجتمعِ دیگر را برنگرداند.

**قاعدهٔ تصمیم:**

| اگر منطق…                                 | تستش اینجاست    |
| ----------------------------------------- | --------------- |
| خالص است (ورودی → خروجی، بدونِ دیتابیس)   | `tests/Unit`    |
| به کوئری، مجوز، تراکنش یا مسیر وابسته است | `tests/Feature` |
| در مرورگر رخ می‌دهد (فرم، حالت، رندر)     | `tests/js`      |
| فقط با مرورگرِ واقعی معنی دارد            | `tests/e2e`     |

🔴 **هر کلاسِ خالصِ تازه‌ای که ساخته شود، تستش باید در لایهٔ واحد باشد.**
`PenaltyCalculator` نمونهٔ چیزی است که این قاعده را نداشت: داکبلاکش
می‌گفت «خالص نگه داشته شده تا تستِ واحدش ساده باشد» و آن تست **هرگز
نوشته نشده بود** — تا R68.

## سیاههٔ قواعدِ کسب‌وکار

⚠️ بیش از هزار تست داشتیم و **هیچ‌جا نوشته نبود کدام قاعده را کدام تست
تضمین می‌کند**.

`tests/Feature/BusinessRulesTest.php` این را می‌بندد: هر قاعده یک جمله
است، به کلاسِ اجراکننده‌اش و **نامِ تستِ ضامنش** گره خورده.

ده دامنه، همان‌ها که در برنامهٔ کار خواسته شده‌اند:

**شارژ** · **تخفیف** · **جریمه** · **کیف پول** · **پرداخت** ·
**دسترسی** · **اشتراک** · **اعلان** · **نظرسنجی** · **مدیریت واحد**

**سه محافظ نگهش می‌دارند:**

| محافظ                                       | چه چیزی را می‌گیرد                                   |
| ------------------------------------------- | ---------------------------------------------------- |
| تستِ ضامنِ هر قاعده باید وجود داشته باشد    | تستی که حذف یا تغییرِ نام بدهد                       |
| هیچ دامنه‌ای خالی نماند                     | استخراجِ ناقص                                        |
| هر کلاسِ بحرانی دستِ‌کم یک قاعده داشته باشد | کلاسی که پول جابه‌جا می‌کند و هیچ ادعای مکتوبی ندارد |

🔴 **و همین سیاهه، در همان اجرای اول یک شکاف پیدا کرد:** قاعدهٔ «تخفیف
نمی‌تواند قبض را منفی کند» — یک `max(0, …)` در `BillGenerator` که کلِ
محافظت را انجام می‌دهد — هیچ تستی نداشت.

### ⚠️ مرزِ این سیاهه

ثابت نمی‌کند قاعده **درست** پیاده شده؛ آن کارِ خودِ تستِ نام‌برده‌شده
است. اینجا فقط تضمین می‌شود قاعده‌ای بی‌ضامن نماند.

## هدفِ پوشش برای بخش‌های Critical

🔴 **هدفِ پوشش اینجا «درصد» نیست، و این یک تصمیم است نه سهل‌انگاری.**

⚠️ درصدِ پوشش **خطِ اجراشده** را می‌شمارد، نه **قاعدهٔ تضمین‌شده**. کلاسی
می‌تواند صددرصد پوشش داشته باشد و هیچ ادعای معناداری رویش نباشد — کافی
است تستی صدایش بزند و خروجی را نسنجد. عددِ سبزِ نودوپنج درصد، اطمینانی
می‌سازد که پشتش چیزی نیست.

**به‌جایش، معیار این است:** هر کلاسِ بحرانی باید دستِ‌کم یک قاعدهٔ
ثبت‌شده در سیاهه داشته باشد، و یک تست آن را قفل کند.

فهرستِ بحرانی — هر چیزی که **پول جابه‌جا می‌کند** یا **مرزِ دسترسی
می‌کشد**:

```
ChargeCalculator · PenaltyCalculator · BillGenerator
WalletService · PaymentService
PlanGate · TenureService · PollService
ComplexScope
```

⚠️ افزودنِ کلاسِ تازه به این فهرست، تست را قرمز می‌کند تا وقتی قاعده‌اش
نوشته شود. یعنی فهرست خودش دروازه است، نه یادداشت.

## دادهٔ تست: کارخانه‌ها

⚠️ پیش از R68 فقط **سه** کارخانه وجود داشت (`User`، `Complex`، `Unit`) و
تست‌ها بقیه را دستی می‌ساختند.

اندازه‌گیری نشان داد پرتکرارترین‌ها کدام‌اند:

| مدل            | ساختِ دستی در تست‌ها |
| -------------- | -------------------- |
| `Bill`         | ۲۴ بار               |
| `Subscription` | ۱۳ بار               |
| `Payment`      | ۱۰ بار               |
| `Expense`      | ۶ بار                |
| `Announcement` | ۳ بار                |

🔴 **تکرارِ دستی فقط زشت نیست، خطرناک است:** ستونِ اجباریِ تازه‌ای که
اضافه شود باید در **همهٔ** آن نقاط به‌روز شود، وگرنه تست‌هایی می‌شکنند
که ربطی به آن تغییر ندارند — و برنامه‌نویس وقتش را صرفِ تعمیرِ داربست
می‌کند نه کد.

**شش کارخانهٔ تازه ساخته شد** — همان‌ها که اندازه‌گیری نشانشان داد.

⚠️ **و نه بیشتر.** ساختنِ کارخانه برای هر ۳۶ مدل، ۳۰ فایلِ بی‌مصرف
می‌سازد که باید نگهداری شوند. کارخانه وقتی ارزش دارد که تکرارِ واقعی را
حذف کند.

هر کارخانه `state`های معنادار دارد (`overdue`، `paid`، `active`،
`distributed`) — چون ترکیبِ ستون‌ها معنی دارد: قبضی که سررسیدش گذشته ولی
وضعیتش «پرداخت‌شده» است، حالتِ ناممکنی است که تستِ جریمه را بی‌معنی
می‌کند.

## پوششِ Endpointها

**۴۶ از ۴۶ کنترلر** دستِ‌کم یک تست دارند — اندازه‌گیری‌شده با نگاشتِ
**مسیر** به کنترلر، نه با جستجوی نامِ کلاس.

⚠️ **نکتهٔ روش:** تست‌ها کنترلر را از راهِ مسیر صدا می‌زنند، پس گرپ‌کردنِ
نامِ کلاس عددِ کاملاً غلط می‌دهد. همین اشتباه یک بار در R48 رخ داد
(«۴۵ از ۵۱ بی‌تست») و عددِ درست پس از اصلاحِ روش **۵ از ۴۶** شد. آن پنج
هم در همان مرحله بسته شدند.

## 🔴 آنچه عمداً سنجیده **نمی‌شود**

| مورد                    | چرا                                                                       |
| ----------------------- | ------------------------------------------------------------------------- |
| بارِ واقعی و نقطهٔ شکست | سرورِ واقعی لازم دارد ([`LOAD_TESTING.md`](LOAD_TESTING.md))              |
| Firefox و WebKit        | فقط Chromium نصب است؛ افزودنشان یک خط است هر وقت لازم شد                  |
| دستگاهِ موبایلِ واقعی   | شبیه‌سازیِ viewport ممکن است، دستگاه نه                                   |
| بازیابیِ بکاپ روی MySQL | رفت‌وبرگشت روی SQLite سنجیده می‌شود؛ رفتارِ کلیدِ خارجی در MySQL فرق دارد |
| ایمیل                   | ⚠️ عمداً در پروژه وجود ندارد                                              |
| Push                    | ⚠️ ساخته نشده؛ تنها کانالِ اعلان، درون‌برنامه‌ای است                      |
| پیامکِ غیر از کدِ ورود  | ⚠️ طبقِ تصمیم، تنها پیامکِ سامانه کدِ ورود است                            |

⚠️ **نبودنِ تست برای چیزی که وجود ندارد، شکاف نیست.** ولی نوشتنش لازم
است، وگرنه بازبینِ بعدی همان راه را دوباره می‌رود.

## اجرا

```bash
php artisan test                      # همهٔ تست‌های PHP
php artisan test --filter=Wallet      # یک دامنه
composer analyse                      # PHPStan
npm test                              # Vitest
npx playwright test                   # سرتاسری
```

⚠️ سرتاسری پیش‌نیازِ داده دارد (دیتابیسِ تازه با `DemoSeeder`، `otp_disabled`
و `E2eSeeder`، و درگاهِ آزمایشیِ اشتراک)؛ فهرستِ دقیق در `DEVELOPER_GUIDE.md`
و `.github/workflows/ci.yml`.

⚠️ **دروازهٔ CI هیچ‌کدام را نادیده نمی‌گیرد** و `--max-warnings=0` دارد:
هشدارِ پذیرفته‌شده، ظرفِ یک ماه می‌شود صد هشدار که کسی نمی‌خواندشان.
