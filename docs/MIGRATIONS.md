# مهاجرتِ امن (R57)

سه چیز در این سند: الگوی **Expand → Migrate → Contract**، قاعده‌ی
**مهاجرتِ مخرب**، و رویه‌ی **«مهاجرتِ اشتباه اجرا شد»**.

> ⚠️ هر سه با تست اجباری شده‌اند، نه فقط نوشته. `MigrationSafetyTest`
> برگشت‌پذیریِ **تک‌به‌تکِ** هر ۴۹ مهاجرت را می‌سنجد و
> `php artisan migrate:check` در `deploy.yml` پیش از `migrate` می‌دود.

---

## ۱) Expand → Migrate → Contract

⚠️ **مشکلی که این الگو حل می‌کند:** در لحظه‌ی استقرار، کدِ قدیم و کدِ جدید
**هم‌زمان** زنده‌اند — کارگرهای صف هنوز نسخه‌ی قبل را اجرا می‌کنند و
درخواست‌های نیمه‌تمام هنوز در راه‌اند. مهاجرتی که ستونی را حذف یا تغییرِ نام
دهد، همان لحظه کدِ قدیم را می‌شکند.

پس هر تغییرِ ناسازگار به **سه استقرارِ جدا** شکسته می‌شود:

| گام          | مهاجرت                                | کد                                           |
| ------------ | ------------------------------------- | -------------------------------------------- |
| **Expand**   | ستون/جدولِ تازه اضافه شود، `nullable` | هنوز از قدیم می‌خواند، در **هر دو** می‌نویسد |
| **Migrate**  | دادهٔ قدیم به تازه کپی شود            | از تازه می‌خواند، در هر دو می‌نویسد          |
| **Contract** | ستونِ قدیم حذف شود                    | فقط تازه                                     |

⚠️ **بین Expand و Contract باید دستِ‌کم یک استقرارِ کامل فاصله باشد.** اگر
هر سه را یک‌جا بفرستید، دقیقاً همان چیزی را ساخته‌اید که الگو می‌خواست
جلویش را بگیرد.

### نمونه‌ی عینی

تغییرِ نامِ `units.area` به `units.area_sqm`:

```
❌ یک مهاجرت:  $table->renameColumn('area', 'area_sqm');
```

کدِ قدیم که هنوز روی سرور می‌دود، `area` را نمی‌یابد و هر محاسبه‌ی شارژ
می‌شکند.

```
✅ سه مهاجرت:
   1) addColumn('area_sqm')->nullable()      ← کد در هر دو می‌نویسد
   2) update: area_sqm = area                ← کد از area_sqm می‌خواند
   3) dropColumn('area')  + @destructive     ← کد فقط area_sqm
```

---

### نمونه‌ی واقعی در مخزن: پیام‌رسانِ گفت‌وگومحور (فاز ۱۲)

| گام          | وضعیت                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Expand**   | ✅ `2026_09_28_000001_create_conversations` — جدول‌های تازه و `conversation_id`ِ nullable                                |
| **Migrate**  | ✅ همان مهاجرت `ConversationBackfill` را اجرا می‌کند؛ کد از گفت‌وگو می‌خواند و `audience`/`unit_id` را هم می‌نویسد       |
| **Contract** | ⏳ استقرارِ بعدی: حذفِ `audience`، `unit_id`، `message_units`، شاخه‌ی قدیمِ `Message::visibleTo` و `GET/POST /messenger` |

⚠️ اگر کد پس از این مهاجرت به نسخه‌ی قبل برگردد، نسخه‌ی قبل پیامِ بی‌گفت‌وگو
می‌نویسد. پس از استقرارِ دوباره:

```bash
php artisan messenger:backfill-conversations
```

تکرارش بی‌خطر است. تا اجرایش هم آن پیام‌ها با قاعده‌ی قبلی — و همان حریم،
با واحدهای **فعلی** — دیده می‌شوند.

## ۲) مهاجرتِ مخرب

عملیاتی که **داده را از بین می‌برند**:

- حذفِ ستون (`dropColumn` / `DROP COLUMN`)
- تغییرِ نامِ ستون (`renameColumn`)
- تغییرِ نوعِ ستون (`->change()` / `MODIFY COLUMN`)
- حذف یا تغییرِ نامِ جدول (`Schema::drop`, `Schema::rename`)
- حذفِ ردیف (`->delete()`, `DELETE FROM`, `TRUNCATE`)

⚠️ `down()` این‌ها را برنمی‌گرداند. ستونِ حذف‌شده را می‌شود دوباره ساخت،
ولی **محتوایش رفته است**.

### قاعده

هر مهاجرتی که در `up()`ِ خود یکی از این‌ها را دارد، باید در docblockش خطِ
زیر را داشته باشد — با دلیلی که دستِ‌کم ۲۰ نویسه باشد:

```php
/**
 * @destructive جدولِ X حذف می‌شود. سنجیده شد که در محصول خالی است و هیچ
 * کدی به آن نمی‌نویسد.
 */
```

بدونِ آن، `php artisan migrate:check` با کدِ خطا برمی‌گردد و **استقرار
پیش از دست‌خوردنِ دیتابیس می‌ایستد**.

⚠️ دلیل اجباری است و عمدی: `@destructive`ِ تنها فقط یک مهرِ لاستیکی
می‌شد. نوشتنِ دلیل، نویسنده را یک بار وادار می‌کند به آنچه از بین می‌رود
فکر کند.

امروز **یک** مهاجرت در کلِ تاریخچه مخرب است و پذیرشِ صریح دارد:
`2026_01_03_000002_drop_message_restrictions_table`.

---

## ۳) برگشت‌پذیری

⚠️ **`migrate:reset` برگشت‌پذیری را اثبات نمی‌کند.** اندازه‌گیری شد: روی هر
۴۹ مهاجرت اجرا شد، همه `DONE` دادند و فقط جدولِ `migrations` ماند. به نظر
می‌رسد همه‌چیز درست است.

ولی ۳۴ مهاجرت از نوعِ `Schema::create` اند و `down()`شان جدول را **کامل**
می‌اندازد. پس اگر مهاجرتی که بالای آن‌ها ستون اضافه کرده `down()`ِ ناقصی
داشته باشد، هیچ‌کس نمی‌فهمد — جدول همان پایین‌تر به‌کل حذف می‌شود.

سنجشِ واقعی **تک‌به‌تک** است: برای هر مهاجرت عکسِ schema و تعدادِ ردیف‌ها
گرفته می‌شود، `up` و بعد `down` اجرا می‌شود، و وضعیت باید **دقیقاً** به
حالتِ اول برگردد. `MigrationSafetyTest` همین را می‌کند.

همان سنجش دو نقصِ واقعی پیدا کرد که `reset` نمی‌دیدشان:

| مهاجرت                            | نقص                                                                                                   |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `seed_default_plans`              | `down()` اسلاگِ `pro` را پاک می‌کرد ولی `up()` پکیج را با `plus` درج کرده بود — یک ردیفِ یتیم می‌ماند |
| `drop_message_restrictions_table` | `down()` جدول را با ستونِ اشتباه و **بدونِ** کلیدِ یکتا بازمی‌ساخت                                    |

## ۴) رویه: «مهاجرتِ اشتباه اجرا شد»

⚠️ **اول تصمیم بگیرید کدام حالت است.** این دو رویه‌ی متفاوت‌اند و
قاطی‌کردنشان وضع را بدتر می‌کند.

### حالت الف — مهاجرت **مخرب نبود** (فقط ستون/جدول اضافه کرد)

```bash
php artisan down --render=errors::503 --retry=30
```

```bash
php artisan migrate:rollback --step=1 --force
```

سپس کد را به نسخه‌ی قبل برگردانید و `php artisan up`.

⚠️ چون برگشت‌پذیریِ تک‌به‌تک تست دارد، این مسیر قابلِ اتکاست.

### حالت ب — مهاجرت **مخرب بود** (ستون یا ردیف حذف شد)

⚠️ **`migrate:rollback` نزنید.** `down()` ساختار را برمی‌گرداند ولی
**داده را نه**؛ و اگر بزنید، حالتِ دیتابیس عوض می‌شود و بازیابی از بکاپ
سخت‌تر.

۱. سایت را ببندید: `php artisan down --render=errors::503`
۲. بکاپِ **پیش از استقرار** را پیدا کنید — `deploy.yml` هر بار پیش از
`rsync` یکی می‌سازد.
۳. از پنلِ ادمینِ کل یا با دستورِ بازیابی برگردانید.
۴. ⚠️ **نوشته‌های پنجره‌ی استقرار از بین می‌روند.** پیش از بازیابی،
بازه‌ی زمانی را یادداشت کنید تا بدانید چه چیزی باید دستی جبران شود.
۵. کد را به نسخه‌ی قبل برگردانید، بعد `php artisan up`.

### در هر دو حالت

```bash
php artisan health:check
```

و رویداد را در `docs/PROJECT_MEMORY.md` بنویسید — با علتِ ریشه‌ای، نه فقط
«مهاجرت خراب بود».

---

## ۵) پیش از هر استقرار

```bash
php artisan migrate:check
```

مهاجرت‌های در انتظار را فهرست می‌کند و روی مخربِ نپذیرفته می‌ایستد. در
`deploy.yml` پیش از `migrate` می‌دود، ولی محلی هم بزنیدش تا نتیجه را قبلِ
push ببینید.
