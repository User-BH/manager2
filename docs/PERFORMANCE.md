## 🔴 سه چیزی که اندازه‌گیری پیدا کرد

### ① `retry_after` ده برابر کوچک‌تر از مهلتِ کارها بود

کنارِ هم گذاشتنِ دو عدد کافی بود:

```
config/queue.php   retry_after            =  90 ثانیه
BuildBillsBundleJob::$timeout             = 900 ثانیه
BuildBackupJob::$timeout                  = 600 ثانیه
BaseJob::$timeout                         = 300 ثانیه
```

`retry_after` یعنی «اگر کاری این‌قدر طول کشید، فرض کن کارگرش مرده و دوباره
تحویلش بده».

🔴 پس سندِ دستهٔ قبضِ یک مجتمعِ ۲۰۰ واحدی — که **دقیقاً برای همین** در صف
است، چون دقایق طول می‌کشد — بعد از نود ثانیه به کارگرِ دوم هم داده می‌شد.
با `tries = 3`، تا سه ساختِ هم‌زمانِ یک سند روی یک رکورد.

هیچ خطایی نمی‌داد. فقط کارِ دوبرابر و رقابت روی همان ردیف.

**رفع:** `retry_after = 1020` (بلندترین مهلت + ارفاق) و یک تست که این را
از **خودِ کلاس‌های کار** مشتق می‌کند: هر Jobی که `$timeout`اش از
`retry_after` بگذرد، تست را قرمز می‌کند.

⚠️ هزینه‌اش صادقانه: کاری که واقعاً یخ بزند (مثلاً `kill -9` روی کارگر)
حالا تا ۱۷ دقیقه منتظر می‌ماند. معامله عمدی است — تأخیر در حالتِ نادر،
به‌جای کارِ تکراری در حالتِ عادی.

### ② پرترافیک‌ترین مسیر، دو کوئریِ بیهوده داشت

`GET /api/v1/notifications` را **هر کاربرِ واردشده هر شصت ثانیه** می‌زند؛
هیچ مسیرِ دیگری در این سامانه چنین ضریبی ندارد. اندازه‌گیری ده کوئری نشان
داد که دوتایش کارِ اضافه بود:

| اتلاف                       | علت                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------ |
| شمارشِ پیام‌رسان **دو بار** | یک بار برای سطرِ فهرست، یک بار در `unreadCount()` — کوئریِ یکسان                     |
| `readIds` با فهرستِ خالی    | `whereIn('id', [])` به `and 0 = 1` ترجمه می‌شود: رفت‌وبرگشتی که قطعاً خالی برمی‌گردد |

**۱۰ ← ۸ کوئری.** سه تست نگهش می‌دارند، و یکی‌شان صریح می‌سنجد که **هیچ
کوئریِ تکراری** در این مسیر نباشد.

### ③ سه ماه دادهٔ کارایی جمع می‌شد و هیچ‌کس نمی‌توانست ببیندش

R38 سنجه‌های Core Web Vitals را از دستگاهِ کاربرانِ واقعی جمع می‌کرد و نود
روز نگه می‌داشت. جست‌وجوی کلِ کد نشان داد این جدول **فقط نوشته می‌شود**:
`WebVitalsController::store` درج می‌کند، `web-vitals:prune` پاک می‌کند، و
هیچ‌کس هرگز نمی‌خواندش.

⚠️ حتی `WebVital::percentile75()` — که دقیقاً برای همین ساخته شده بود و
توضیحش می‌گفت چرا میانگین جوابِ اشتباه می‌دهد — **صفر فراخوانی** داشت.

همان الگوی R64 (`backups.status`): ستونی که نوشته می‌شود و خوانده نمی‌شود.

**رفع:** `php artisan perf:baseline`.

## `perf:baseline`

```bash
php artisan perf:baseline            # ۲۸ روزِ گذشته
php artisan perf:baseline --days=7
```

سه بخش: صدکِ ۷۵ِ هر سنجه به تفکیکِ دستگاه، حجمِ جدول‌های رشدی، و وضعیتِ صف.

⚠️ **چرا صدکِ ۷۵ و نه میانگین:** سایتی که ۷۰٪ کاربرانش تجربهٔ عالی و ۳۰٪
تجربهٔ افتضاح دارند، میانگینِ قابلِ‌قبول می‌گیرد و در Search Console مردود
می‌شود. صدک آن دُمِ بد را نشان می‌دهد. این همان معیاری است که خودِ گوگل با
آن قضاوت می‌کند.

⚠️ **کمبودِ نمونه صریح گفته می‌شود.** صدکِ ۷۵ روی سه نمونه، عددِ سومی است
نه صدک. زیرِ ۳۰ نمونه، گزارش «نمونه کم» می‌زند تا کسی بر اساسِ نویز
بهینه‌سازی نکند.

⚠️ **و نبودِ داده هم صریح گفته می‌شود.** جدولِ خالی خیلی راحت «همه‌چیز خوب
است» خوانده می‌شود، در حالی که دقیقاً یعنی هیچ‌چیز سنجیده نشده.

🔒 **چرا امروز عددی نیست:** سایت هنوز ترافیکِ واقعی ندارد. این تنها راهِ
درستِ گرفتنِ این عدد است — دادهٔ آزمایشگاهی (Lighthouse روی لپ‌تاپِ
توسعه‌دهنده) چیزی است که در رتبهٔ جستجو اثر ندارد.

## عددهای اندازه‌گیری‌شده

### کوئری و حجمِ پاسخ

روی مجتمعی با ۴۰ واحد، کشِ دیتابیسی:

| مسیر                        | کوئری      | حجمِ پاسخ |
| --------------------------- | ---------- | --------- |
| `GET /` (فرود، HTML)        | ۲          | ۱۱٫۶KB    |
| `GET /api/v1/me`            | ۳          | ۴۰۵B      |
| `GET /api/v1/ads`           | ۳          | ۱٫۷KB     |
| `GET /api/v1/bills`         | ۵          | ۹۱۶B      |
| `GET /api/v1/residents`     | ۵          | ۱٫۴KB     |
| `GET /api/v1/payments`      | ۵          | ۸۷B       |
| `GET /api/v1/finance`       | ۵          | ۱٫۸KB     |
| `GET /api/v1/units`         | ۶          | ۵٫۸KB     |
| `GET /api/v1/notifications` | ۸ (بود ۱۰) | ۲۸B       |
| `GET /api/v1/dashboard`     | ۲۳         | ۹۰۸B      |

⚠️ **بندِ ۲۶۶ (API Payload / DTO) سالم است:** سنگین‌ترین پاسخ ۵٫۸KB برای
۴۰ واحد است، یعنی ~۱۴۶ بایت به ازای هر واحد. هیچ مدلی کامل serialize
نمی‌شود.

⚠️ **داشبورد با ۲۳ کوئری سنگین‌ترین است** و این عمدی است: یک صفحه، ده
تجمیعِ مالیِ متفاوت. کوئری‌ها با تعدادِ ردیف رشد **نمی‌کنند** (سنجهٔ
`QueryProfileTest`)، پس مسئلهٔ N+1 نیست. بهینه‌سازی‌اش بدونِ عددِ زمانِ
واقعیِ سرور، حدس است — و آن عدد کارِ R66 است.

### حافظه

```
/api/v1/dashboard      افزایش ۴MB
/api/v1/notifications  افزایش ۲MB
/api/v1/units          افزایش ۰MB
/                      افزایش ۰MB
```

⚠️ **مقدارِ مطلق NOT MEASURED است.** اوجِ حافظه از داخلِ PHPUnit خوانده
می‌شود و ۷۶MBِ گزارش‌شده تقریباً همه‌اش مالِ خودِ فرایندِ تست است، نه
درخواست. عددِ مطلق فقط از یک پردازهٔ واقعیِ PHP-FPM درمی‌آید.

عددِ افزایشی ولی معنی‌دار است و **نشتی نشان نمی‌دهد**: مسیرهای سبک صفر
می‌مانند.

### بارِ polling

| منبع            | فاصله    | درخواست بر ساعت بر کاربر    | شرط                      |
| --------------- | -------- | --------------------------- | ------------------------ |
| زنگولهٔ اعلان   | ۶۰ ثانیه | ۶۰                          | فقط وقتی تب دیده می‌شود  |
| پیام‌رسان       | ۸ ثانیه  | ۴۵۰                         | فقط وقتی صفحه‌اش باز است |
| به‌روزرسانیِ SW | ۳۰ دقیقه | ۲                           | —                        |
| صفحهٔ بکاپ      | متغیر    | فقط تا پایانِ کارِ در جریان | —                        |

با بیست کاربرِ آنلاین و پنج نفر داخلِ پیام‌رسان: **حدود یک درخواست بر
ثانیه.**

## دو تصمیمی که با عدد گرفته شدند

### 🔴 Redis: **نه** — و شرطی که نظر را عوض می‌کند

هزینهٔ واقعیِ کش و نشستِ دیتابیسی، اندازه‌گیری‌شده:

```
کشِ دیتابیسی    ۱ کوئری در هر درخواست (تنظیمات و پرچم‌ها)
نشستِ دیتابیسی  ۲ کوئری در هر درخواست (خواندن + نوشتن)  ← ذاتیِ درایور
```

یعنی Redis روی هم **سه رفت‌وبرگشتِ محلی** را حذف می‌کند. روی یک سرور با
MySQLِ همان ماشین، هر کدام کسری از میلی‌ثانیه است.

در مقابلش: یک سرویسِ تازه برای نصب، پایش، امن‌سازی و تصمیم‌گیری دربارهٔ
بکاپش — و قیدِ صریحِ پروژه: «بیخودی پکیج نصب نکن».

⚠️ **ولی عددی که نظر را عوض می‌کند از قبل مشخص است، و ربطی به سرعت
ندارد:**

🔴 **به‌محضِ اینکه برنامه روی بیش از یک گره اجرا شود، کشِ اشتراکی از یک
موضوعِ کارایی به یک موضوعِ درستی تبدیل می‌شود.** خفه‌کنِ هشدار (R64)، قفلِ
`withoutOverlapping` زمان‌بند، و محدودکنندهٔ نرخِ ورود همگی روی کش
می‌نشینند. با دو گره و کشِ محلی، هر کدام نیمی از حقیقت را می‌بینند: هشدار
دو بار می‌رود و محدودکنندهٔ نرخ دو برابر اجازه می‌دهد.

کشِ دیتابیسیِ امروز **اشتراکی است** و همین حالا این خاصیت را دارد. پس
تصمیم این است: تا وقتی عددِ زمانِ پاسخِ سرور (R66) نگوید کش گلوگاه است،
چیزی عوض نمی‌شود.

### 🔴 Real-Time (WebSocket / SSE): **نه** — با همان عدد

بارِ کلِ polling در مقیاسِ امروز **حدود یک درخواست بر ثانیه** است.

⚠️ WebSocket برای این پروژه یعنی یک پردازهٔ دائمیِ تازه (Reverb یا
مشابهش)، پیکربندیِ پروکسیِ nginx برای ارتقای اتصال — که **قیدِ صریحِ پروژه
دست‌نزدن به آن است** — و یک مسیرِ خرابیِ تازه که کاربر آن را به شکلِ
«پیام‌ها نمی‌آیند» می‌بیند.

و مهم‌تر: هیچ‌کدام از قابلیت‌های این سامانه واقعاً بی‌درنگ نیستند. اطلاعیه،
قبض و رسید همه دورهٔ زندگی‌شان روزانه است. تنها جای نزدیک به بی‌درنگ
پیام‌رسان است، که همین حالا هر هشت ثانیه به‌روز می‌شود.

⚠️ **عددی که نظر را عوض می‌کند:** وقتی بارِ polling به چند ده درخواست بر
ثانیه برسد، یا وقتی قابلیتی بیاید که تأخیرِ هشت‌ثانیه‌ای برایش قابلِ قبول
نباشد. `perf:baseline` و `alerts:scan` هر دو داده‌اش را می‌دهند.
