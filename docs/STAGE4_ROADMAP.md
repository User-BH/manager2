## قاعدهٔ صفر — منبعِ حقیقت

🔴 **گزارش‌های قبلی منبعِ حقیقتِ قطعی نیستند.** آن‌ها فقط _شاهد_ و
*تاریخچه*‌اند.

منبعِ حقیقتِ نهایی از سه چیز ساخته می‌شود:

1. **کدِ واقعیِ مخزن**
2. **رفتارِ واقعیِ تست‌ها**
3. مستنداتِ نهایی **پس از** Cross-check

⚠️ هرجا گزارشِ قبلی با کدِ واقعی اختلاف داشت، **کد و تست بر گزارش اولویت
دارند** — حتی اگر آن گزارش را خودم نوشته باشم.

---

## چرخهٔ اجباریِ هر مورد

هیچ موردی پیش از عبور از این شش گام Complete محسوب نمی‌شود:

```
Inventory → Inspect → Fix → Test → Adversarial Test → Regression → Document
```

🔴 **و صریح‌تر: هیچ موردی صرفاً با این کارها «تمام‌شده» اعلام نمی‌شود** —
تغییرِ مستندات، افزودنِ تستِ صوری، عوض‌کردنِ برچسبِ وضعیت، یا نوشتنِ جملهٔ
«already implemented».

## واژگانِ وضعیت — جایگزینِ نشانه‌های قبلی

⚠️ نشانه‌های قدیمی (✅ / 🟡 / 🔒 / ❌ / ❓) کنار گذاشته می‌شوند. از این
پس **فقط** این شش برچسب:

| برچسب                                                        | یعنی                                                              |
| ------------------------------------------------------------ | ----------------------------------------------------------------- |
| **VERIFIED**                                                 | کد + تست + اجرای موفق + بررسیِ واقعی                              |
| **IMPLEMENTATION READY — ENVIRONMENT VERIFICATION REQUIRED** | کد آماده است؛ اثباتِ نهایی محیطِ واقعی می‌خواهد                   |
| **INTENTIONALLY NOT BUILT**                                  | عمداً در دامنه نیست، با دلیلِ فنی/محصولیِ مستند                   |
| **BLOCKED BY EXTERNAL ENVIRONMENT**                          | فقط به‌دلیلِ نبودِ سرور، دستگاه، درگاه یا سرویسِ بیرونی           |
| **OPEN**                                                     | واقعاً هنوز نقص دارد                                              |
| **HISTORICAL FINDING RESOLVED**                              | زمانی نقص بود، واقعاً رفع شده؛ نباید مثلِ نقصِ باز نمایش داده شود |

🔴 **در پایان، هیچ موردِ `OPEN` با شدتِ Critical/High که داخلِ مخزن
قابلِ‌حل باشد نباید بماند.**

**② عددِ polling بی‌پشتوانه.** ✅ **بسته شد — و نتیجه‌اش خلافِ حدسم بود.**
نوشته بودم شاید polling اصلاً وجود ندارد؛ اشتباه بود: در
`features/notifications/` گشته بودم ولی polling در
`shared/stores/notificationStore.ts` است. عددِ «≈ ۱ درخواست بر ثانیه»
**درست بود**؛ آنچه کم بود مبنا و واحد بود. جزئیات در
[`CANONICAL_INVENTORY.md`](CANONICAL_INVENTORY.md).

**③ خرابکاری جایگزینِ پوشش نیست.** `FINAL_TEST_REPORT.md` خرابکاری را
«معیارِ جایگزین» پوشش نامیده. ⚠️ اصلاحیه صریح می‌گوید این دو **هدفِ
متفاوت** دارند. متن باید اصلاح شود: نبودِ پوشش با دلیلش ثبت شود، و
خرابکاری به‌عنوانِ چیزِ دیگری معرفی شود.

## فاز ۱ — یکپارچگیِ مالی · ✅ **انجام شد**

**اندازه:** XL · **خروجی:** سه نقصِ مالی بسته شد، ۲۳ تستِ تازه

🔴 **دو مورد از سه یافتهٔ فاز ۰ اشتباه صورت‌بندی شده بودند** و کاوشِ تجربی
هر دو را اصلاح کرد. جزئیات در [`CANONICAL_INVENTORY.md`](CANONICAL_INVENTORY.md).

### ۱) نوعِ مجتمع

رفتارِ درست:

```
missing complex_type  → validation failure
invalid complex_type  → validation failure
residential           → residential rules
commercial            → commercial rules
```

🔴 **هیچ پیش‌فرضِ خطرناکی برای طبقه‌بندیِ حیاتیِ کسب‌وکار پذیرفته نیست.**
و دامنهٔ پلن باید سمتِ سرور اعمال شود: کاربر نتواند نوع را جعل کند، پلنِ
نامرتبط بخرد، تعرفهٔ نامرتبط بگیرد، یا با تغییرِ بدنهٔ درخواست دور بزند.

### ۲) تغییرناپذیریِ دفتر — روی هشت بردار

`update` · `delete` · `forceDelete` · mass assignment · دست‌کاریِ رابطه ·
به‌روزرسانیِ مستقیمِ دیتابیس · به‌روزرسانیِ دسته‌ای · کوئریِ خام

⚠️ محافظت باید **سه‌لایه** باشد: لایهٔ برنامه (مدل/سرویس/سیاست)، لایهٔ
دیتابیس (قید و معناشناسی)، لایهٔ کسب‌وکار (اصلاح فقط با سندِ معکوس).

### ۳) 🔴 ناوردایی موجودی ↔ دفتر — **الزامِ تازه**

⚠️ **تغییرناپذیرکردنِ `WalletTransaction` به‌تنهایی کافی نیست.** باید
ثابت شود:

- هیچ مسیرِ عادی نمی‌تواند `balance` را **بدونِ** ایجادِ تراکنشِ معتبر عوض کند
- اصلاحِ اشتباهِ مالی فقط از مسیرِ reversal/correction
- موجودیِ منفی بدونِ قاعدهٔ معتبرِ کسب‌وکار ممکن نیست
- عملیاتِ همزمان نه دوباره‌شماری می‌کند نه تراکنش گم می‌کند
- همهٔ تغییراتِ مالی atomic‌اند
- **منبعِ حقیقتِ مالی دقیقاً مشخص است**

🔴 اگر `balance` مستقیماً قابلِ تغییر است، آن مسیر هم ممیزی و اصلاح شود.

### ۴) ماشینِ حالتِ پرداخت

برای هر گذار `FROM → TO = ALLOWED / FORBIDDEN` صریح شود.

⚠️ **از وضعیت‌های واقعیِ پروژه استفاده شود؛ وضعیتِ تازه بی‌دلیل اضافه
نشود.** و هیچ controller/service/job نتواند `status` را دلخواه mutate کند.

### ۵) Idempotency

`lockForUpdate()` به‌تنهایی کافی نیست — به‌خصوص وقتی رکورد هنوز وجود
ندارد. لازم است: کلیدِ idempotencyِ کسب‌وکار، قیدِ یکتای دیتابیس، و پوششِ
درخواستِ تکراری، دابل‌کلیک، درخواست‌های همزمان، بازپخشِ callback،
راستی‌آزماییِ مکرر، و کارِ retry.

### ۶) درستیِ مبلغ

🔴 **هیچ مبلغی از کلاینت مورد اعتماد نیست.** سرور منبعِ حقیقت است؛
ناهمخوانی باید رد و ممیزی شود.

### ۷) راستی‌آزماییِ درگاه

⚠️ **ادعای «درگاه‌های ایرانی callback را امضا نمی‌کنند» را حقیقتِ جهانی
فرض نمی‌کنیم** — حتی با اینکه خودم در `FINAL_SECURITY_REPORT` نوشته‌امش.
باید روی **درگاهِ واقعیِ همین پروژه** بررسی شود. اگر امضا واقعاً نیست،
دلیلش باید **مخصوصِ همان یکپارچه‌سازی** و مستند باشد.

### ۸) معناشناسیِ کلیدِ خارجی و حذف

حذفِ والد نباید تاریخچهٔ مالی را نابود کند.

## فاز ۷ — صف، آپلود، SSRF · ✅ **انجام شد**

**اندازه:** M · **خروجی:** حاشیهٔ صریحِ `retry_after`، سیاههٔ SSRF با شاهد،

SSRF: سیاههٔ هر ورودی‌ای که به مقصدِ شبکه می‌رسد. ⚠️ اگر قابلیتی اصلاً
SSRF-capable نیست، **با شاهد** مشخص شود.
