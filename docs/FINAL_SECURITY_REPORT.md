## S-01 · اعتبارنامهٔ درگاه و پیامک به‌صورتِ متنِ ساده در دیتابیس

| فیلد             | مقدار                                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **شدت**          | 🔴 **بحرانی**                                                                                                                                                                                     |
| **مؤلفه**        | `complex_settings` — کلیدِ درگاه، رمزِ ترمینال، توکنِ پیامک                                                                                                                                       |
| **مشکل**         | کلیدها همان‌طور که وارد می‌شدند ذخیره می‌شدند                                                                                                                                                     |
| **سناریوی حمله** | 🔴 هر مسیری که به **خواندنِ** دیتابیس برسد، پول را هم می‌برد: یک SQLi خواندنی، یک بکاپِ گم‌شده، یا یک اپراتورِ phpMyAdmin. مهاجم بی‌آنکه به سرور دست بزند، از ترمینالِ خودِ مجتمع تراکنش می‌سازد. |
| **اصلاح**        | رمزنگاری در سطحِ ویژگی با `SecretValue` + مهاجرتِ `encrypt_stored_credentials` که مقادیرِ موجود را هم رمز کرد                                                                                     |
| **راستی‌آزمایی** | `SecretHandlingTest` (۱۵ تست) — از جمله اینکه مقدارِ خام هرگز در دیتابیس ننشیند و `toArray()` آن را برنگرداند                                                                                     |

⚠️ **باقی‌مانده:** `SecretValue` هنوز مقدارِ متنِ سادهٔ قدیمی را می‌خواند تا
مهاجرت روی همهٔ نصب‌ها اجرا شود. برداشتنِ این تحملْ گامِ ۳ از M-01 است.

## S-02 · نتیجهٔ تسویه نادیده گرفته می‌شد

## S-10 · دورهٔ کنترل‌شده از کاربر در نامِ فایلِ خروجیِ اکسل

| فیلد             | مقدار                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **شدت**          | 🟠 **بالا** (CVE-2026-84374 · `GHSA-c7r6-vx3h-w5g2`)                                                                                                                     |
| **مؤلفه**        | `maatwebsite/excel` ۳٫۱٫۶۹ + `DownloadController::billsExport`                                                                                                           |
| **مشکل**         | `?period=` بدونِ هیچ اعتبارسنجی در نامِ فایل می‌نشست: `'bills-'.$period.'.xlsx'`، و نسخه‌های پیش از ۳٫۱٫۷۰ با مسیرِ کنترل‌شده بیرونِ دیسکِ پیکربندی‌شده می‌نویسند        |
| **سناریوی حمله** | 🔴 مدیرِ یک مجتمعِ پرو `?period=../../../../` می‌فرستد و خروجی جایی بیرونِ دیسکِ تعیین‌شده نوشته می‌شود. ⚠️ نیازمندِ حسابِ معتبرِ پرو است، پس مهاجمِ ناشناس دسترسی ندارد |
| **اصلاح**        | ① بسته به **۳٫۱٫۷۰** به‌روز شد · ② `$period` با `/^\d{4}-\d{2}$/` سنجیده می‌شود و در غیرِ این صورت ۴۲۲ — همان الگوی `StoreDiscountRequest`                               |
| **راستی‌آزمایی** | `DocumentExportTest` — پنج بردار (پیمایشِ یونیکسی، پیمایشِ ویندوزی، جداکنندهٔ مسیر، بایتِ تهی، پسوندِ دیگر) به‌علاوهٔ تستی که مطمئن می‌شود دورهٔ سالم هنوز کار می‌کند    |

🔴 **چطور پیدا شد، و چرا این مهم‌ترین نکتهٔ این ردیف است:** کارِ امنیتیِ CI
در فاز ۹ قرمز شد. مشاوره **همان روز، ساعتِ ۲۰:۴۰** منتشر شده بود — یعنی
پس از آخرین اجرای سبز.

⚠️ کدِ ما عوض نشده بود؛ **دنیا** عوض شده بود. پس «CI دیروز سبز بود» دلیلِ
امن‌بودنِ امروز نیست، و `composer audit --locked` باید **پیش از هر
استقرار** دوباره اجرا شود.

## امنیتِ callbackِ درگاه — پاسخ به بندهای ۴۸ تا ۵۳

⚠️ این ردیف‌ها تا R72 مبهم مانده بودند. پاسخِ صریح، از روی کدِ واقعی:

| بند | محور          | وضعیت | چرا                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | ------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ۴۸  | Signature     | ✅    | ⚠️ **مخصوصِ همین دو یکپارچه‌سازی است، نه یک حقیقتِ جهانی** — نسخهٔ قبلی این را قاعده‌ای دربارهٔ «درگاه‌های ایرانی» نوشته بود. بازبینیِ فاز ۱ کد را سنجید: در `MellatGateway` و `SamanGateway` هیچ امضا، HMAC یا hashی وجود ندارد. اصالت با **فراخوانِ سرور‌به‌سرور** (`bpVerifyRequest` و `VERIFY_URL` سامان) با اعتبارنامهٔ ترمینال ثابت می‌شود و خودِ callback هرگز مبنای تسویه نیست. 🔴 اگر روزی درگاهی امضا داشته باشد، باید از آن استفاده شود |
| ۴۹  | Replay        | ✅    | پرداختِ نهایی‌شده دوباره پردازش نمی‌شود؛ `GatewayCallbackTest` تکرارِ همان callback را می‌سنجد                                                                                                                                                                                                                                                                                                                                                     |
| ۵۰  | Timestamp     | 🔒    | ⚠️ **موضوعیت ندارد** — این درگاه‌ها زمان‌مُهرِ امضاشده‌ای در callback نمی‌فرستند که بشود سنجید. حفاظتِ هم‌ارز همان verifyِ سمتِ سرور است                                                                                                                                                                                                                                                                                                           |
| ۵۱  | Idempotency   | ✅    | قفلِ ردیف + سنجشِ وضعیت؛ `ConcurrencyTest::test_settling_the_same_payment_twice_is_a_no_op`                                                                                                                                                                                                                                                                                                                                                        |
| ۵۲  | IP validation | 🔒    | ⚠️ **عمداً ساخته نشد:** بانک‌ها فهرستِ پایدارِ IP منتشر نمی‌کنند. سیاههٔ کهنه یعنی پرداخت‌های واقعی رد شوند — و با verifyِ سمتِ سرور، افزودهٔ امنیتی‌اش صفر است                                                                                                                                                                                                                                                                                    |
| ۵۳  | Rate Limiting | ✅    | محدودکنندهٔ `gateway-callback`، ۳۰ در دقیقه به‌ازای IP                                                                                                                                                                                                                                                                                                                                                                                             |
