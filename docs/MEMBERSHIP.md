# عضویت — پایه‌ی داده (مرحلهٔ ۱۰ · فاز ۲)

> بندهای ۳، ۴، ۱۱ و ۱۳ ِ فایلِ معماری. نقشه‌ی کل: [`ARCHITECTURE_EVIDENCE_MAP.md`](ARCHITECTURE_EVIDENCE_MAP.md).

تا پیش از این فاز «عضویت» فقط `users.complex_id` + `users.role` بود: یک مقدار، بی شروع، بی پایان،
بی تاریخچه. حالا هر عضویتِ یک حساب در یک مجتمع ردیفِ `complex_memberships` است.

```
حساب (users) ──┬── عضویت در مجتمعِ الف — active   (نقش، منبع، شروع)
               ├── عضویت در مجتمعِ ب   — ended    (پایان، پایان‌دهنده، دلیل)
               └── …
```

| ستون                     | معنا                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| `role`                   | `owner`، `tenant` یا `complex_admin` — ادمینِ کل نقشِ سکوست و عضویت ندارد        |
| `status`                 | `active` یا `ended` — «در انتظار»، «ردشده» و «ابطال‌شده» مالِ دعوت و درخواست‌اند |
| `source`                 | `invitation`، `join_request`، `purchase`، `direct` (دادهٔ نمونه)، `backfill`     |
| `invitation_id`          | دعوت یا درخواستی که عضویت را ساخت                                                |
| `started_at`، `ended_at` | شروع و پایان                                                                     |
| `ended_by`، `end_reason` | چه کسی و چرا: `removed` (پایانِ عضویت) یا `promoted` (ارتقا به ادمینِ کل)        |
| `active_key`             | فقط برای عضویتِ فعال پر و یکتا: یک عضویتِ فعال برای هر (حساب، مجتمع)             |

## قاعده‌ها و جایی که سنجیده می‌شوند

| قاعده                                                                 | کجا                                                                                 |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| تنها نویسنده‌ی عضویت و زمینه‌ی فعالِ حساب `MembershipLedger` است      | `User` تغییرِ `complex_id` / `role` را بیرون از آن رد می‌کند (`LogicException`)     |
| هر مسیرِ واقعی ردیفِ خودش را می‌سازد: دعوت، درخواستِ پیوستن، خرید     | `MembershipLedgerTest`                                                              |
| پایانِ عضویت حذفِ حساب نیست؛ ردیف با زمان، پایان‌دهنده و دلیل می‌ماند | `MembershipLedgerTest`، `TransitionDataIntegrityTest`                               |
| تاریخچه با حذفِ حساب یا مجتمع پاک نمی‌شود                             | `restrictOnDelete` (بندِ ۷۹)                                                        |
| یک عضویتِ فعال برای هر (حساب، مجتمع)                                  | ایندکسِ یکتای `active_key`                                                          |
| وضعیت، نقش و شکلِ چرخه‌ی عمر                                          | قیدهای CHECK (`SchemaConstraintTest` روی MySQL ِ CI)                                |
| مدیر فقط عضویت‌های مجتمعِ خودش را می‌خواند                            | `BelongsToComplex` (`TenantScopeCoverageTest`)                                      |
| هم‌زمانی: یک پذیرش یا یک خرید، یک عضویتِ فعال                         | `InvitationConcurrencyTest`، `CheckoutConcurrencyTest` (پردازه‌ی واقعی، MySQL ِ CI) |

## قاعده‌ی امروز: یک عضویتِ فعال برای هر حساب

schema چند عضویتِ فعال در **مجتمع‌های مختلف** را می‌پذیرد؛ سرویس هنوز نه. دلیل: مجوز هنوز از
`users.complex_id` (زمینه‌ی فعال) خوانده می‌شود، و عضویتِ دوم بی زنجیره‌ی مجوزِ مبتنی بر عضویت یعنی
دسترسی‌ای که هیچ لایه‌ای نمی‌سنجد. برداشتنِ این قاعده با ۱۰/۳ است.

## دادهٔ موجود و استقرار

مهاجرتِ `2026_10_11_000001_create_complex_memberships_table` به هر حسابِ عضوِ موجود (مالک، مستأجر یا
مدیر با `complex_id`) یک عضویتِ فعال با منبعِ `backfill` می‌دهد؛ شروع = قدیمی‌ترین دوره‌ی واحدِ او در همان
مجتمع، وگرنه زمانِ ساختِ حساب. عضویت‌های **پایان‌یافته‌ی** پیش از این مهاجرت حدس زده نمی‌شوند: سابقه‌شان
در دوره‌های واحد (`unit_user`) و ردِ حسابرسی است. ادمینِ کل و حسابِ اولیه عضویت نمی‌گیرند.

پس از مهاجرت روی هر محیط:

```bash
php artisan memberships:check
```

هر حسابِ عضو باید عضویتِ فعالِ هم‌خوان داشته باشد و هیچ عضویتِ فعالی بی‌صاحب نماند؛ فرمان چیزی را درست
نمی‌کند — فقط می‌گوید. روی رونوشتِ پایگاه‌داده‌ی توسعه (۱۰ حسابِ عضو) مهاجرت ۱۰ عضویت ساخت و فرمان
هم‌خوانی را تأیید کرد. روی محصول: پس از استقرار، با بکاپِ پیش از مهاجرتِ `deploy.sh`.
