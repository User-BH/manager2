# عضویت — پایه‌ی داده (مرحلهٔ ۱۰ · فاز ۲)

> بندهای ۳، ۴، ۱۱ و ۱۳ ِ فایلِ معماری. نقشه‌ی کل: [`ARCHITECTURE_EVIDENCE_MAP.md`](ARCHITECTURE_EVIDENCE_MAP.md).

تا پیش از این فاز «عضویت» فقط `users.complex_id` + `users.role` بود: یک مقدار، بی شروع، بی پایان،
بی تاریخچه. حالا هر عضویتِ یک حساب در یک مجتمع ردیفِ `complex_memberships` است.

```
حساب (users) ──┬── عضویت در مجتمعِ الف — active   (نقش، منبع، شروع)
               ├── عضویت در مجتمعِ ب   — ended    (پایان، پایان‌دهنده، دلیل)
               └── …
```

| ستون                     | معنا                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| `role`                   | `owner`، `tenant` یا `complex_admin` — ادمینِ کل نقشِ سکوست و عضویت ندارد        |
| `status`                 | `active` یا `ended` — «در انتظار»، «ردشده» و «ابطال‌شده» مالِ دعوت و درخواست‌اند |
| `source`                 | `invitation`، `join_request`، `purchase`، `direct` (دادهٔ نمونه)، `backfill`     |
| `invitation_id`          | دعوت یا درخواستی که عضویت را ساخت                                                |
| `started_at`، `ended_at` | شروع و پایان                                                                     |
| `ended_by`، `end_reason` | چه کسی و چرا: `removed` (پایانِ عضویت) یا `promoted` (ارتقا به ادمینِ کل)        |
| `active_key`             | فقط برای عضویتِ فعال پر و یکتا: یک عضویتِ فعال برای هر (حساب، مجتمع)             |

## قاعده‌ها و جایی که سنجیده می‌شوند

| قاعده                                                                 | کجا                                                                                 |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| تنها نویسنده‌ی عضویت و زمینه‌ی فعالِ حساب `MembershipLedger` است      | `User` تغییرِ `complex_id` / `role` را بیرون از آن رد می‌کند (`LogicException`)     |
| هر مسیرِ واقعی ردیفِ خودش را می‌سازد: دعوت، درخواستِ پیوستن، خرید     | `MembershipLedgerTest`                                                              |
| پایانِ عضویت حذفِ حساب نیست؛ ردیف با زمان، پایان‌دهنده و دلیل می‌ماند | `MembershipLedgerTest`، `TransitionDataIntegrityTest`                               |
| تاریخچه با حذفِ حساب یا مجتمع پاک نمی‌شود                             | `restrictOnDelete` (بندِ ۷۹)                                                        |
| یک عضویتِ فعال برای هر (حساب، مجتمع)                                  | ایندکسِ یکتای `active_key`                                                          |
| وضعیت، نقش و شکلِ چرخه‌ی عمر                                          | قیدهای CHECK (`SchemaConstraintTest` روی MySQL ِ CI)                                |
| مدیر فقط عضویت‌های مجتمعِ خودش را می‌خواند                            | `BelongsToComplex` (`TenantScopeCoverageTest`)                                      |
| هم‌زمانی: یک پذیرش یا یک خرید، یک عضویتِ فعال                         | `InvitationConcurrencyTest`، `CheckoutConcurrencyTest` (پردازه‌ی واقعی، MySQL ِ CI) |

## چند عضویت و زمینه‌ی فعال (۱۰/۳)

یک حساب می‌تواند در چند مجتمع عضوِ فعال باشد — یکی برای هر مجتمع. `users.complex_id` و `users.role`
**زمینه‌ی فعال** است: مجتمعی که حساب الان در آن کار می‌کند و نقشش در همان. دادهٔ مجتمعِ دیگر در این زمینه دیده
نمی‌شود (دامنه‌ی مستأجر) و نقش همان نقشِ عضویتِ همین‌جاست — مدیرِ الف که به ب (مالک) می‌رود دیگر مدیر نیست.

| کار                       | رفتار                                                                                                                                                           |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET account/memberships` | عضویت‌های فعالِ **خودِ** حساب و اینکه کدام زمینه‌ی فعال است                                                                                                     |
| `POST account/context`    | رفتن به مجتمعی که عضویتِ فعال دارد؛ وگرنه ۴۲۲ ِ یکسان (وجودِ مجتمع لو نمی‌رود)؛ ادمینِ کل از پنلِ سیستم انتخاب می‌کند                                           |
| پیوستن                    | عضویتِ تازه و رفتن به زمینه‌ی آن                                                                                                                                |
| پایانِ عضویت              | فقط در **همان** مجتمع — عضویت و دوره‌ی واحدِ مجتمع‌های دیگر دست نمی‌خورند؛ اگر زمینه‌ی فعال بود، حساب به تازه‌ترین عضویتِ فعالِ دیگرش می‌رود، وگرنه حالتِ اولیه |
| تغییرِ نقش                | فقط عضویتِ همان مجتمع؛ زمینه‌ی فعال فقط اگر همان مجتمع باشد                                                                                                     |

### زنجیره‌ی مجوز روی هر درخواست

```
حساب ← فعال ← عضویتِ فعال در همین مجتمع با همین نقش ← نقش ← رابطه‌ی واحد ← policy
```

`SetCurrentComplex` مجتمعِ جاری را **همراهِ** سنجشِ عضویت می‌خواند (همان یک کوئری که پیش از این هم بود). اگر
زمینه‌ی روی حساب عضویتِ فعالِ هم‌خوان نداشته باشد — پایان‌یافته، نقشِ دست‌کاری‌شده — درخواست ۴۰۳ با
`membership.inactive` می‌گیرد، نه بازگشت به مجتمعِ دیگر؛ خروج از حساب آزاد است.

### خواننده‌ها از عضویت

فهرستِ ساکنان و مدیران، جست‌وجوی مدیر، مخاطبانِ مدیریت، کارگزارانِ درخواستِ خدمات، اعلانِ درخواستِ پیوستن به
مدیران، شمارِ اعضای مجتمع، بکاپِ مجتمع، قاعده‌ی انتقالِ مالکیت و سیاست‌های `UserPolicy` اعضا را از **عضویت**
می‌خوانند (`ComplexMembers`)، با نقشِ عضویتِ همان مجتمع: عضوِ ب که الان در الف کار می‌کند همچنان ساکنِ ب است.
دوره‌ی واحد (`TenureService::open`) فقط درونِ همان مجتمع «جابه‌جایی» حساب می‌شود.

### پیوستن برای عضوِ مجتمعِ دیگر و تعویض در رابط (۱۰/۴)

دعوت و درخواستِ پیوستن عضوِ مجتمع‌های دیگر را هم راه می‌دهند؛ فقط عضویتِ دوم در **همان** مجتمع رد می‌شود.
پذیرفتن یا تأیید عضویتِ تازه‌ای کنارِ قبلی‌ها می‌سازد — عضویت و دوره‌ی واحدِ مجتمعِ دیگر دست نمی‌خورند، و دعوتِ
مجتمعِ سوم با پیوستن نمی‌میرد. پیوستن به زمینه‌ی مجتمعِ تازه می‌برد.

| در رابط                      | رفتار                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| «مجتمع‌های من» در منوی کاربر | فقط وقتی حساب در بیش از یک مجتمع عضو است؛ مجتمعِ فعال نشان‌دار — برای حسابِ تک‌مجتمعی منو همان قبلی است |
| «دعوت‌ها (n)»                | عضوِ دعوت‌شده به مجتمعِ دیگر؛ دعوت‌ها در «پروفایلِ من»، فقط وقتی هست                                    |
| تعویض یا پیوستن              | `enterNewContext`: کشِ API ِ Service Worker پاک، تب‌های دیگرِ حساب از نو بار، ناوبریِ کامل به داشبورد   |
| کشِ React Query              | هر کلید با «حساب و مجتمعِ فعال» درهم‌سازی می‌شود؛ کشِ الف در ب پاسخ داده نمی‌شود                        |

**خریدِ مجتمعِ تازه** از ۱۰/۵ برای عضو هم باز است — بخشِ «خریدِ مجتمعِ تازه با حسابِ عضو» در پایین.

## دو مسیرِ ورود: QR ِ عمومی و دعوتِ مستقیم (۱۰/۵)

بندهای ۲۱ تا ۲۵ و ۹۰ ِ فایلِ معماری: دو مسیر جدا می‌مانند و مدیر تفاوتشان را در رابط می‌بیند.

| مسیر         | گام‌ها                                                                     | تأییدِ مدیر | به چه بسته است                     |
| ------------ | -------------------------------------------------------------------------- | ----------- | ---------------------------------- |
| QR ِ عمومی   | اسکن ← `/join` (نامِ مجتمع) ← ثبت‌نام/ورود ← درخواست ← تأیید ← عضویتِ فعال | لازم        | هیچ شخصی — فقط مجتمع را نام می‌برد |
| دعوتِ مستقیم | «ساکن جدید» ← پیوندِ شخصی ← ثبت‌نام ← عضویت ← داشبوردِ واحد                | نه          | یک شماره؛ یک‌بارمصرف و هفت‌روزه    |

**QR ِ عمومی.** هر مجتمع حداکثر یک کد دارد (`complexes.join_code`، ۱۲۸ بیت در base64url). کد متنِ ساده است
نه هش، چون روی QR ِ لابی چاپ می‌شود و مدیر باید دوباره ببیندش؛ «راز» نیست، فقط حدس‌نزدنی است تا مجتمع‌ها
پیموده نشوند. «نمایشِ QR» کدِ موجود را نگه می‌دارد، «QR ِ تازه» قبلی را همان لحظه باطل می‌کند و «خاموش» ورودِ
عمومی را می‌بندد؛ درخواست‌های فرستاده‌شده در هر سه حالت می‌مانند. پیش‌نمایش (`join-link/preview`) برای مهمان و
حسابِ اولیه فقط نامِ مجتمع را می‌دهد؛ کدِ بدشکل، باطل‌شده، با حروفِ عوض‌شده یا مجتمعِ تعلیق‌شده همه ۴۰۴ ِ
یکسان‌اند. درخواست همان `POST join-requests` است که با شماره‌ی مدیر هم کار می‌کند و تا تأییدِ مدیر هیچ
عضویتی نمی‌سازد. کد در `#` ِ نشانی است و پیش از پایش و تحلیل پاک می‌شود؛ برای برگشت پس از ورود در
`sessionStorage` ِ همان تب می‌ماند — فقط مسیریابیِ رابط، نه مجوز.

**دعوتِ مستقیم پس از ثبت‌نام (بندِ ۹۰).** اگر ثبت‌نام از پیوندِ دعوت باشد، توکن همراهِ کدِ ثبت‌نام می‌رود و
`AuthController::registerVerify` — اگر دعوت زنده، مستقیم و برای **همین شماره** باشد — همان‌جا
`Membership::accept` را صدا می‌زند؛ ورودِ بعدی داشبوردِ واحد است و داشبوردِ اولیه دیده نمی‌شود. کدِ پیامکیِ
جدای پذیرش لازم نیست، چون ثبت‌نام همیشه کدِ پیامکیِ همان شماره را می‌خواهد (`otp_disabled` هم آن را برنمی‌دارد —
`DirectInvitationRoutingTest` می‌سنجد). توکنِ نامعتبر، مصرف‌شده یا برای شماره‌ی دیگر ثبت‌نام را خراب نمی‌کند:
حساب در حالتِ اولیه ساخته می‌شود و دعوتِ زنده‌ی همان شماره در داشبورد منتظر است (بندِ ۹۱). کسی که از قبل
حساب دارد همان مسیرِ قبلی را دارد: ورود و پذیرش با کدِ پیامکی.

**QR بی بسته‌ی تازه.** رمزگذار (`resources/js/shared/lib/qrCode.ts`) بایت‌مود، سطحِ M، نسخه‌ی ۱ تا ۱۰ است.
`tests/js/qrCode.test.ts` خروجی را با ماتریس‌های **رمزگذارِ مستقلِ OpenCV 4.13** برای هر ده نسخه می‌سنجد: با
ماسکِ OpenCV ماژول‌به‌ماژول یکی‌اند، جز یک بیتِ باقی‌مانده در نسخه‌ی ۵ (OpenCV آن را ماسک نمی‌کند؛ استاندارد
صفر می‌گذارد و خواننده‌ها نادیده‌اش می‌گیرند). محلی، رمزگشای OpenCV ۴۷ از ۴۸ QR ِ ساخته‌شده را خواند (۴۰ نشانیِ
`/join#…` ِ تصادفی، نسخه‌های ۱، ۲، ۴، ۶، ۹ و ۱۰، و متنِ فارسی). تنها استثنا «HELLO WORLD» با ماسکِ ۴ در بزرگ‌نماییِ
۸ و ۱۲ بود؛ همان رمزگشا خروجیِ رمزگذارِ خودِ OpenCV برای همین متن را هم نخواند، و QR ِ ما در بزرگ‌نماییِ ۴ خوانده
شد.

## خریدِ مجتمعِ تازه با حسابِ عضو (۱۰/۵؛ تصمیمِ کارفرما)

هر حسابِ فعالِ غیرِ سکو با همان حسابِ canonical مجتمعِ تازه می‌خرد، حتی با عضویتِ فعال در مجتمع‌های دیگر:
مالکِ A و مستأجرِ B، پس از خریدِ معتبر مدیرِ C.

**تعارضی که ثبت و برداشته شد:** سه نگهبانِ `account.already_member` (در `ComplexPurchase::begin`،
`ComplexPurchase::complete` و `ComplexUpgrader::upgrade`) فقط حسابِ اولیه را راه می‌دادند و پرداختِ عضو را به
`paid_unfulfilled` می‌بردند؛ و یک مسیرِ `subscription/checkout` «خریدِ مجتمع» و «تمدید» را فقط از «اولیه بودن»
جدا می‌کرد. هیچ قاعده‌ی تجاریِ دیگری (سقفِ تعدادِ خرید و مانند آن) در کد نبود.

| قاعده                              | کجا                                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- |
| خرید یا تمدید — صریح               | `purpose=new_complex`؛ حسابِ اولیه همیشه خرید. تمدید همچنان فقط مدیرِ همان مجتمع                |
| چه کسی می‌خرد                      | `SubscriptionPolicy::purchaseComplex` — فعال و غیرِ سکو                                         |
| پلن، مبلغ و مدت                    | از سرور: پلنِ قابلِ خرید و هم‌نوع، مبلغ و مدت از پلن؛ یک قصدِ باز برای هر حساب                  |
| ساختن فقط پس از تأییدِ درگاه، اتمی | `ComplexPurchase::complete` زیرِ قفلِ قصد و `TrackingCodes::exclusively`؛ بازگشتِ تکراری بی‌اثر |
| A و B دست نمی‌خورند                | عضویت، نقش، واحد، دوره، کیف، اشتراک و ردیفِ مجتمع؛ زمینه‌ی فعالِ عضو هم جابه‌جا نمی‌شود         |
| رفتن به C                          | کلاینت پس از بازگشت `POST account/context` (سرور با عضویت می‌سنجد) و `enterNewContext`          |
| مدیر در C، هیچ در A و B            | زنجیره‌ی مجوزِ ۱۰/۳ از زمینه‌ی فعال و عضویتِ همان مجتمع                                         |

**چرا زمینه‌ی عضو جابه‌جا نمی‌شود:** بازگشتِ درگاه (و تأییدِ درخواست به دستِ مدیر) کارِ خودِ کاربر در این
تب نیست؛ جابه‌جاییِ سمتِ سرور تب‌های بازِ او را بی‌خبر به مجتمعِ دیگر می‌برد و داده‌ی تازه زیرِ کلیدِ کشِ
قبلی می‌نشست. پس `MembershipLedger::start(..., activate: false)` حسابِ دارای زمینه را سرِ جایش نگه می‌دارد؛
حسابِ اولیه — که زمینه‌ای ندارد — همان‌جا وارد می‌شود. همین رفع برای تأییدِ درخواستِ پیوستن هم اعمال شد:
تأییدِ مدیرِ B متقاضی‌ای را که در A کار می‌کند به B نمی‌برد.

## دادهٔ موجود و استقرار

مهاجرتِ `2026_10_11_000001_create_complex_memberships_table` به هر حسابِ عضوِ موجود (مالک، مستأجر یا
مدیر با `complex_id`) یک عضویتِ فعال با منبعِ `backfill` می‌دهد؛ شروع = قدیمی‌ترین دوره‌ی واحدِ او در همان
مجتمع، وگرنه زمانِ ساختِ حساب. عضویت‌های **پایان‌یافته‌ی** پیش از این مهاجرت حدس زده نمی‌شوند: سابقه‌شان
در دوره‌های واحد (`unit_user`) و ردِ حسابرسی است. ادمینِ کل و حسابِ اولیه عضویت نمی‌گیرند.

پس از مهاجرت روی هر محیط:

```bash
php artisan memberships:check
```

هر حسابِ عضو باید عضویتِ فعالِ هم‌خوان داشته باشد و هیچ عضویتِ فعالی بی‌صاحب نماند؛ فرمان چیزی را درست
نمی‌کند — فقط می‌گوید. روی رونوشتِ پایگاه‌داده‌ی توسعه (۱۰ حسابِ عضو) مهاجرت ۱۰ عضویت ساخت و فرمان
هم‌خوانی را تأیید کرد. روی محصول: پس از استقرار، با بکاپِ پیش از مهاجرتِ `deploy.sh`.
