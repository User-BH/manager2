# جست‌وجوی مدیر — مرحلهٔ ۱۰ · فاز ۸

بندهای ۲۰، ۴۱، ۸۲ و ۱۲۱ ِ فایلِ معماری. دو جست‌وجو هست و هر دو یک کمکِ مشترک دارند:

| جست‌وجو          | مسیر                                             | چه کسی                             |
| ---------------- | ------------------------------------------------ | ---------------------------------- |
| کلی (سربرگ)      | `GET /api/search?q=&group=&page=`                | همه؛ واحد، ساکن و قبض فقط مدیر     |
| فهرستِ گفت‌وگوها | `GET /api/v1/messenger/conversations?q=&cursor=` | مدیر؛ ساکن فقط عنوانِ گروه و کانال |

## عبارت چطور خوانده می‌شود (`App\Support\SearchTerm`)

یک بار یکدست می‌شود: `%` و `_` حذف، «ي/ى/ك» ← «ی/ک»، اعرابِ کوتاه («مالکِ واحدِ») حذف، فاصله‌ها یکی. ارقامِ
فارسی برای شماره‌ی واحد، تلفن و کدِ ملی لاتین می‌شوند. سپس:

| عبارت            | معنا                                                        |
| ---------------- | ----------------------------------------------------------- |
| `۱۰`             | هر واحدی که ۱۰ در شماره‌اش هست، و ساکنانِ **خودِ** واحدِ ۱۰ |
| `واحد ۱۰`        | فقط واحدِ ۱۰                                                |
| `مالک واحد ۱۰`   | مالکِ **فعلیِ** واحدِ ۱۰ (دوره‌ی بسته به حساب نمی‌آید)      |
| `مستأجر واحد ۲۵` | مستأجرِ فعلیِ واحدِ ۲۵؛ واحدِ بی‌مستأجر هیچ                 |
| `ساکن واحد ۲۵`   | هر دو                                                       |
| `علی احمدی`      | نام، تلفن یا کدِ ملیِ اعضای **فعالِ** همین مجتمع            |

در پیام‌رسان همان عبارت به رشته‌ی آن واحد می‌رسد (رشته‌ی خصوصیِ امروز مالِ واحد است؛ ساختارِ فرد‌به‌فرد: ۱۰/۹)،
و نامِ ساکنِ بی‌واحد به رشته‌ی خودش.

## مرز

- **مجتمع از عضویت است، نه از درخواست.** پارامترِ `complex_id` نادیده گرفته می‌شود؛ ادمینِ کل مجتمع را از نشست
  می‌گیرد و جست‌وجوی پیام‌رسان همان را صریح دریافت می‌کند.
- **`CommunityLookup`** هر زیرپرسش را با `complex_id` ِ صریح می‌نویسد، بی تکیه بر دامنه‌ی سراسری. لایه‌های بیرونی
  (دامنه‌ی `Unit`، پیوندِ عضویت، دامنه‌ی گفت‌وگو) هم هستند — خرابکاری نشان داد هر کدام به‌تنهایی جلوی نشت را
  می‌گیرد؛ آزمونِ مستقیمِ کمک مرزِ خودش را هم می‌سنجد.
- **پیام‌رسان پس از `visibleTo`:** جست‌وجو فقط باریک می‌کند. ساکن با آن حتی رشته‌ی خودش را با نام یا شماره پیدا
  نمی‌کند (بندِ ۴۲ جست‌وجو را برای او الزامی نمی‌داند)؛ هیچ گفت‌وگویی ساخته نمی‌شود.
- **مجتمعِ دیگر = پاسخِ تهی، نه خطا** (بندِ ۱۲۱: «fail/empty/403 طبق API contract»): پاسخِ ۴۰۳ خودش می‌گفت چیزی
  آن‌جا هست.
- **تاریخچه‌ی جست‌وجو** در مرورگر با کلیدِ `app:recent-searches:{حساب}:{مجتمع}` است؛ پیش از ۱۰/۸ یک کلیدِ
  سراسری بود و «علی احمدی — ۳ نتیجه» ِ مدیرِ الف در ب و برای حسابِ بعدی هم دیده می‌شد. کلیدِ قدیم پاک می‌شود.

## صفحه‌بندی و کارایی

- نمای کلی هر گروه را در ۸ می‌بُرد و `hasMore` می‌گوید؛ «نمایشِ همه‌ی …» گروه را با `group` باز می‌کند و
  صفحه‌ها (۲۰ تایی، `page` تا ۱۰۰) پشتِ هم می‌آیند. پیش از ۱۰/۸ رابط هیچ راهی به نهمی نداشت.
- فهرستِ گفت‌وگوها همان نشانگرِ `last_message_id:id` را دارد؛ رابط تا ۱۰/۸ فقط ۳۰ تای اول را می‌خواند.
- هر جست‌وجو زیرپرسش است، نه فهرستِ شناسه در حافظه: شمارِ کوئری با اندازه‌ی مجتمع ثابت می‌ماند
  (`ManagerSearchTest`، `ConversationSearchTest`).
- نمایه‌ها: `units(complex_id, unit_number)` ِ یکتا، `unit_user(unit_id, relation, is_current)`،
  `complex_memberships(complex_id, status)`. جست‌وجوی نام `LIKE '%…%'` است و هیچ نمایه‌ی B-tree آن را نمی‌گیرد؛
  دامنه‌اش اعضای فعالِ همین مجتمع است. سنجشِ ۵۰۰ واحدی روی سرورِ واقعی با بندِ ۱۲۵ است (۱۰/۱۶).
