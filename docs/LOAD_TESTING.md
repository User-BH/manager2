# سنجشِ بار و فشار — رویه، و چیزی که بیشترِ اجراها اشتباه می‌سنجند

> ⚠️ **این سند رویه است، نه نتیجه.** هیچ عددِ ظرفیتی اینجا نیست چون هنوز
> روی سرورِ واقعی اجرا نشده. وضعیتِ این مرحله **NOT VERIFIED** است و
> تا اجرای واقعی همان می‌ماند.

---

## 🔴 چیزی که باید پیش از هر اجرا بدانید

**اجرای بی‌دقتِ سنجشِ بار روی این سامانه، محدودکننده‌ی نرخ را می‌سنجد نه
برنامه را — و عددش بهتر از واقعیت به‌نظر می‌رسد.**

این حدس نیست. اندازه‌گیری‌اش این است:

```
POST /api/v1/web-vitals   هم‌زمانی ۳، شش ثانیه
   موفق  ۱۰      ← دقیقاً همان سقفِ ۱۰ در دقیقه
   ۴۲۹   ۲۷۰
   RPS   ۴۶٫۵
```

و برای مقایسه، مسیری بدونِ سقف روی همان ماشین:

```
GET /up                   هم‌زمانی ۴، شش ثانیه
   موفق  ۲۳۱
   RPS   ۳۸٫۱
```

🔴 **مسیرِ محدودشده RPSِ بالاتری نشان داد.** چون رد‌کردنِ درخواست ارزان‌تر
از سرو‌کردنش است. کسی که فقط ستونِ RPS را نگاه کند، نتیجه می‌گیرد آن مسیر
سریع‌تر است — در حالی که ۹۶٪ کاربرانش خطا گرفته‌اند.

برای همین `scripts/load-probe.php` ستونِ ۴۲۹ را **جدا** می‌شمارد و اگر
صفر نباشد صریح هشدار می‌دهد.

## سقفِ نرخ در هر یک از هشت جریانِ خواسته‌شده

| جریان         | مسیر                        | سقف                                 | برای سنجشِ بار                  |
| ------------- | --------------------------- | ----------------------------------- | ------------------------------- |
| Login         | `POST /api/v1/login`        | ۵/دقیقه هر شماره، ۲۰/دقیقه هر IP    | 🔴 از یک ماشین بی‌معنی است      |
| Dashboard     | `GET /api/v1/dashboard`     | ۶۰/دقیقه هر کاربر (**تازه در R66**) | با کاربرانِ متعدد               |
| Reports       | `POST .../bills-bundle`     | ۱۲/ساعت هر کاربر                    | کارِ صف است، نه مسیرِ وب        |
| Payment       | `GET /pay/{bill}` و بازگشت  | بازگشتِ درگاه ۳۰/دقیقه هر IP        | 🔒 درگاهِ واقعی لازم دارد       |
| Wallet        | `GET /api/v1/wallet`        | بدونِ سقف                           | ✅ مستقیم                       |
| Notifications | `GET /api/v1/notifications` | بدونِ سقف                           | ✅ مستقیم — و پرترافیک‌ترین است |
| Search        | `GET /api/v1/search`        | ۴۰/دقیقه هر کاربر                   | با کاربرانِ متعدد               |
| Messaging     | `GET /api/v1/messenger`     | ۴۰/دقیقه هر کاربر                   | با کاربرانِ متعدد               |

⚠️ سقف‌ها بر پایه‌ی **کاربرِ واردشده** حساب می‌شوند نه IP (جز ورود). پس
سنجشِ درست به چند نشستِ واقعی نیاز دارد، نه چند اتصال از یک کوکی.

### همه‌ی سقف‌های سامانه

⚠️ فهرستِ کامل لازم است: هر مسیری که بسنجید یا در این فهرست هست یا نیست، و
جوابش تفسیرِ عددتان را عوض می‌کند. یک تست هم‌سانیِ این فهرست را با
`AppServiceProvider` می‌سنجد، پس سقفِ تازه‌ای نمی‌تواند بی‌سروصدا اضافه شود.

| نامِ سقف           | سقف                                                                   |
| ------------------ | --------------------------------------------------------------------- |
| `login`            | ۵/دقیقه هر شماره · ۲۰/دقیقه هر IP                                     |
| `otp-request`      | ۳/۱۰دقیقه هر شماره · ۱۵/۱۰دقیقه هر IP · ۱۰/روز · ۶۰/روز هر IP         |
| `otp-verify`       | ۵/دقیقه هر شماره · ۲۰/دقیقه هر IP                                     |
| `register`         | ۵/ساعت هر IP · ۲۰/روز هر IP                                           |
| `gateway-callback` | ۳۰/دقیقه هر IP                                                        |
| `system-restore`   | ۱۰/ساعت (اجرای آزمایشی بی‌سقف)                                        |
| `search`           | ۴۰/دقیقه هر کاربر                                                     |
| `messenger`        | ۴۰/دقیقه هر کاربر                                                     |
| `client-errors`    | ۲۰/دقیقه هر کاربر                                                     |
| `web-vitals`       | ۱۰/دقیقه هر کاربر                                                     |
| `sms-campaign`     | ۵/ساعت هر کاربر                                                       |
| `backups`          | ۱۲/ساعت هر کاربر                                                      |
| `bills-generate`   | ۲۰/ساعت هر کاربر                                                      |
| `support-chat`     | ۲۰/دقیقه هر IP                                                        |
| `receipt-upload`   | ۲۰/ساعت هر کاربر                                                      |
| `dashboard`        | ۶۰/دقیقه هر کاربر — **تازه در R66**                                   |
| `api`              | **سراسری:** ۲۴۰/دقیقه هر کاربر · نوشتن ۶۰/دقیقه                       |
| `messenger-send`   | ۱۰/دقیقه · ۳۰۰/روز هر کاربر                                           |
| `service-requests` | ۵/دقیقه · ۵۰/روز هر کاربر (ثبت و نظر)                                 |
| `password-change`  | ۵/۱۵دقیقه هر کاربر                                                    |
| `reauth`           | ۵/۱۵دقیقه هر کاربر — تأییدِ دوباره‌ی رمز پیش از عملیاتِ حساس (فاز ۱۰) |
| `payment-start`    | ۶/دقیقه · ۳۰/ساعت هر کاربر (قبض و اشتراک)                             |
| `sms-test`         | ۱۰/ساعت هر کاربر                                                      |

✅ **سقفِ سراسری از مرحلهٔ ۵ · فاز ۹.** تا پیش از آن هر مسیری که در این
فهرست نبود بی‌سقف بود — ۱۵۹ مسیرِ تغییردهنده، از جمله ارسالِ پیام. حالا
`api` روی هر مسیرِ `/api` و `/api/v1` است و کلیدش به کاربر بسته است، پس
دو پیشوند یک شمارنده دارند. ⚠️ در سنجشِ بار با **یک** کاربر، این سقف
زودتر از ظرفیتِ سرور می‌رسد؛ کاربرانِ متعدد بسازید.

🔴 **سقف‌ها را برای سنجش پایین نیاورید و برندارید.** آن‌ها بخشی از رفتارِ
محصول‌اند؛ عددی که با سقفِ برداشته‌شده گرفته شود، ظرفیتِ سامانه‌ای است که
مستقر نمی‌شود. اگر می‌خواهید ظرفیتِ خامِ یک مسیر را بدانید، مسیرِ بی‌سقف
(`/up`، `wallet`، `notifications`) را بسنجید.

## ابزار

```bash
php scripts/load-probe.php --url=https://DOMAIN/up --concurrency=100 --duration=30
php scripts/load-probe.php --url=https://DOMAIN/api/v1/notifications \
    --cookie="sakena_session=..." --concurrency=100,500,1000 --duration=30
```

بدونِ هیچ وابستگی — فقط PHP و افزونه‌ی cURL. طبقِ قیدِ پروژه هیچ پکیجی
(k6، ab، wrk) نصب نمی‌شود.

🔴 **از ماشینِ دیگری اجرا کنید.** تولیدکننده‌ی بار روی همان سرور، CPU را
از خودِ برنامه می‌دزدد و عددِ حاصل ترکیبِ دو بار است. اسکریپت خودش وقتی
هدف `localhost` باشد هشدار می‌دهد.

## ⚠️ پیش‌نیازها — بدونِ این‌ها عدد بی‌معنی است

| شرط                        | چرا                                                                  |
| -------------------------- | -------------------------------------------------------------------- |
| `APP_DEBUG=false`          | حالتِ اشکال‌زدایی هر کوئری را در حافظه نگه می‌دارد؛ هم کند و هم نشتی |
| `php artisan config:cache` | بدونش هر درخواست همه‌ی فایل‌های config را می‌خواند                   |
| `php artisan route:cache`  | همان داستان برای مسیرها                                              |
| OPcache روشن               | بدونش PHP هر بار همه‌ی فایل‌ها را دوباره کامپایل می‌کند              |
| `npm run build` انجام‌شده  | بدونش دارایی‌ها اصلاً سرو نمی‌شوند                                   |
| کارگرِ صف بالا             | وگرنه کارهای سنگین انباشته می‌شوند و تصویر عوض می‌شود                |
| دادهٔ واقع‌نما             | مجتمعی با چند واحد، N+1 را پنهان می‌کند                              |

🔴 **و مهم‌ترین شرط: PHP-FPM با چند کارگر.**

`php artisan serve` تک‌پردازه است (درسِ R47). عددی که رویش بگیرید صرفاً
صف‌شدن پشتِ یک پردازه را می‌سنجد: با دو برابر شدنِ هم‌زمانی، تأخیر دو
برابر می‌شود و توان تقریباً ثابت می‌ماند. همان الگو در اجرای بالا هم
دیده می‌شود (۴ هم‌زمان → p50 حدود ۷۸ms).

## حسابِ ظرفیت، پیش از اجرا

⚠️ این‌ها **پیش‌بینی**‌اند نه اندازه‌گیری — ولی از عددهای واقعیِ R65
ساخته شده‌اند و می‌گویند چه چیزی را باید تنظیم کنید تا اجرا اصلاً معنی
بدهد.

**کارگرِ PHP-FPM:**

```
کارگرِ لازم ≈ هم‌زمانی × میانگینِ زمانِ پاسخ (ثانیه)
```

اگر پاسخِ داشبورد ۲۰۰ میلی‌ثانیه باشد، ۱۰۰ کاربرِ هم‌زمان حدودِ **۲۰ کارگر**
می‌خواهد. `pm.max_children` کمتر از این یعنی درخواست‌ها در صفِ FPM
می‌مانند و شما تأخیرِ صف را اندازه می‌گیرید، نه برنامه را.

**اتصالِ دیتابیس:**

```
max_connections ≥ کارگرِ FPM + کارگرِ صف + زمان‌بند + سرِ ریز
```

⚠️ پیش‌فرضِ MySQL معمولاً ۱۵۱ است. با ۲۰۰ کارگرِ FPM، دیتابیس پیش از
برنامه می‌شکند — و پیامِ خطا («Too many connections») به‌سادگی به‌حسابِ
باگِ برنامه گذاشته می‌شود.

**کوئری بر ثانیه** — از جدولِ اندازه‌گیری‌شده‌ی `docs/PERFORMANCE.md`:

| مسیر            | کوئری | ۱۰۰ req/s | ۵۰۰ req/s |
| --------------- | ----- | --------- | --------- |
| `notifications` | ۸     | ۸۰۰       | ۴٬۰۰۰     |
| `units`         | ۶     | ۶۰۰       | ۳٬۰۰۰     |
| `dashboard`     | ۲۳    | ۲٬۳۰۰     | ۱۱٬۵۰۰    |

🔴 **نشست و کش هم روی همان دیتابیس‌اند** و در جدولِ بالا شمرده نشده‌اند:
هر درخواست سه کوئریِ دیگر اضافه می‌کند (خواندنِ نشست، نوشتنِ نشست، خواندنِ
کش). این همان عددی است که در R65 گفته شد تصمیمِ Redis را عوض می‌کند.

## چهار پله، و اینکه هر کدام چه چیزی را ثابت می‌کند

| پله    | چه چیزی را ثابت می‌کند                                                         |
| ------ | ------------------------------------------------------------------------------ |
| ۱۰۰    | پیکربندی درست است: بدونِ ۵xx، تأخیر تقریباً ثابت                               |
| ۵۰۰    | کارگرهای FPM و اتصالِ دیتابیس کافی‌اند؛ اینجا معمولاً اولین صف‌شدن دیده می‌شود |
| ۱٬۰۰۰  | نقطه‌ی زانو: تأخیر شروع به رشدِ غیرخطی می‌کند                                  |
| ۱۰٬۰۰۰ | ⚠️ برای این سامانه بیشتر سنجشِ **زیرساخت** است تا برنامه                       |

⚠️ **۱۰٬۰۰۰ کاربرِ هم‌زمان برای یک سامانه‌ی مدیریتِ مجتمع عددِ واقع‌بینانه‌ای
نیست** و این را باید صریح گفت. اگر هر مجتمع صد واحد داشته باشد، ده هزار
کاربرِ **هم‌زمان** یعنی صدها مجتمع که همه در یک لحظه فعال‌اند. سنجیدنش بد
نیست، ولی نتیجه‌اش عملاً ظرفیتِ nginx و کرنل را می‌گوید نه برنامه را.

**نقطه‌ی شکست** جایی است که یکی از این سه اتفاق بیفتد:

- ۵xx ظاهر شود (هر عددی جز صفر)
- اتصال قطع شود (ستونِ خطای حمل‌ونقل)
- تأخیرِ p95 از حدِ قابلِ استفاده بگذرد (برای این سامانه: بیش از دو ثانیه)

## هنگام و پس از اجرا، این‌ها را ببینید

```bash
php artisan perf:baseline    # حجمِ جدول‌ها و عمقِ صف، پیش و پس از اجرا
php artisan alerts:scan      # جهشِ خطا و شکستِ پرداخت را می‌گیرد
php artisan health:check     # دیسک، صف، زمان‌بند
tail -f storage/logs/laravel.log
```

⚠️ **کدِ پیگیریِ R63 اینجا کار می‌کند:** هر پاسخِ خطا `X-Request-Id` دارد،
پس یک ۵xx در سنجشِ بار را می‌شود مستقیم در لاگ پیدا کرد به‌جای گشتن بر
اساسِ زمان.

🔴 **پس از اجرا، جدول‌ها را پاک کنید.** سنجشِ بار ردیفِ `sessions`،
`cache`، `web_vitals` و `error_events` می‌سازد. اگر روی محصول اجرا
می‌کنید، این ردیف‌ها با دادهٔ واقعی قاطی می‌شوند و آمارِ بعدی را خراب
می‌کنند.
