# هشدار — چه چیزی زنگ می‌زند، چرا، و آن‌وقت چه باید کرد

> این سند دفترچه‌ی هشدارهای سامانه است. برای هر هشدار: چه چیزی را می‌گیرد،
> با چه عددی، **چرا آن عدد**، و اپراتور وقتی زنگ خورد چه کار کند.

---

## 🔴 اول از همه: هشدار به چه کسی می‌رسد؟

⚠️ این پروژه دو قیدِ صریح دارد که کلِ طراحیِ هشدار را شکل داده‌اند:

- **ایمیل کنار گذاشته شده است** — هیچ کانالِ ایمیلی در پروژه نیست.
- **پیامک فقط کدِ ورود است** — هیچ پیامکِ دیگری فرستاده نمی‌شود.

نتیجه‌اش را باید صریح گفت، نه لاپوشانی کرد:

| مسیر                 | همیشه کار می‌کند؟            | کسی را بیدار می‌کند؟        |
| -------------------- | ---------------------------- | --------------------------- |
| کانالِ لاگِ `alerts` | ✅ حتی وقتی دیتابیس مرده است | ❌ کسی باید فایل را باز کند |
| زنگوله‌ی سوپرادمین   | ❌ به دیتابیس نیاز دارد      | ❌ کسی باید وارد پنل شود    |
| `ALERT_WEBHOOK_URL`  | ✅                           | ✅ **تنها مسیر**            |

🔴 **بدونِ `ALERT_WEBHOOK_URL`، هیچ هشداری کسی را خبر نمی‌کند.** هر سرویسی
که یک آدرسِ POST بدهد کار می‌کند. بدنه‌ی ارسالی:

```json
{
  "source": "ساکنا",
  "status": "degraded",
  "problems": { "sms": "هیچ پیامکی نمی‌رود؛ ورود با کد ممکن نیست — ۷ از ۷ ارسال ناموفق (۱۰۰٪)" },
  "at": "2026-09-02T11:15:00+03:30"
}
```

⚠️ متنِ `problems` پیش از ارسال از پاک‌کننده‌ی رازِ R55 رد می‌شود. تا پیش
از R64 نمی‌شد: پیامِ استثنای PDO رشته‌ی اتصال دارد و پیامِ Guzzle آدرسِ
کاملِ درگاهِ پیامک را — که کلیدِ API داخلش است. آن متن‌ها در فایلِ لاگ پاک
می‌شدند ولی از این مسیر دست‌نخورده به یک سرویسِ **بیرونی** می‌رفتند.

## دو خانواده‌ی هشدار، و چرا از هم جدا هستند

|                                   | `health:check` (R43)         | `alerts:scan` (R64)           |
| --------------------------------- | ---------------------------- | ----------------------------- |
| پرسش                              | این گره می‌تواند سرویس بدهد؟ | چیزی به‌طورِ سیستمی خراب شده؟ |
| مبنا                              | یک لحظه                      | روند در یک پنجره              |
| مصرف‌کننده                        | متعادل‌کننده‌ی بار (`/up`)   | آدم                           |
| می‌تواند گره را از مدار خارج کند؟ | ✅                           | ❌ هرگز                       |
| هر چند وقت                        | ۱۵ دقیقه                     | ۱۵ دقیقه                      |

⚠️ **چرا سنجه‌های R64 روی `/up` سوار نشدند:** آن مسیر را متعادل‌کننده‌ی
بار هر چند ثانیه می‌زند. چهار کوئریِ تجمیعی روی هر ضربه، هزینه‌ای است که
تا روزِ شلوغی هیچ‌کس نمی‌بیندش — و آن‌وقت خودِ ابزارِ پایش می‌شود منبعِ
کندی.

⚠️ **پنجره عمداً بلندتر از فاصله‌ی اجراست** (۶۰ دقیقه در برابرِ ۱۵). یعنی
هر خرابی چند بار پشتِ سرِ هم دیده می‌شود. تکرارش را خفه‌کن
(`ALERT_THROTTLE_MINUTES`) می‌بلعد، و در عوض رخدادی که درست بینِ دو اجرا
افتاده از قلم نمی‌افتد. پنجره‌ی چسبیده به فاصله‌ی اجرا، در خرابیِ کوتاه
ساکت می‌ماند.

## دفترچه‌ی هشدارها

### ① جهشِ خطا — `errors`

|            |                                                       |
| ---------- | ----------------------------------------------------- |
| **آستانه** | `ALERT_ERROR_RATE_PER_HOUR` (پیش‌فرض ۶۰)              |
| **شدت**    | `degraded`                                            |
| **مبنا**   | اختلافِ مجموعِ `error_events.occurrences` بین دو اجرا |

🔴 **چرا ردیف شمرده نمی‌شود.** جدولِ `error_events` با اثرِ انگشت گروه
می‌کند: خطایی که ده هزار بار در دقیقه تکرار شود **یک ردیف** است که فقط
`occurrences`اش جلو می‌رود. سنجه‌ای که ردیف بشمارد، دقیقاً بدترین حالت —
یک خطای حلقه‌زده — را نمی‌بیند.

⚠️ **چرا ۶۰:** یعنی به‌طورِ متوسط یک خطا در دقیقه، پیوسته. زیرِ این عدد،
چند خطای پراکنده زندگیِ عادیِ هر سامانه‌ای است.

**دو حالتی که عمداً هشدار نمی‌دهند:**

- اولین اجرا (یا پس از خالی‌شدنِ کش) پایه ندارد → «پایه‌ی شمارش ثبت شد»
- اختلافِ منفی، یعنی جدول هرس شده (`ERROR_LOG_RETENTION_DAYS`) → پایه از
  نو ثبت می‌شود. تفسیرِ عددِ منفی به‌عنوان نرخ یعنی هشدار پس از هر هرس.

**وقتی زنگ زد:** «پایش و تحلیل» در پنلِ ادمینِ کل → پرتکرارترین خطا. کدِ
پیگیریِ R63 (`X-Request-Id`) روی همان ردیف است، پس خطِ لاگِ همان درخواست
با `grep` پیدا می‌شود.

### ② جهشِ شکستِ پرداخت — `payments`

|            |                                                                              |
| ---------- | ---------------------------------------------------------------------------- |
| **آستانه** | `ALERT_PAYMENT_FAILURE_PERCENT` (۵۰) با کفِ `ALERT_PAYMENT_MIN_ATTEMPTS` (۵) |
| **شدت**    | `degraded`                                                                   |
| **مبنا**   | پرداخت‌های آنلاینِ پنجره: `failed` + بلاتکلیف‌های R59                        |

⚠️ **چرا نسبت به‌تنهایی کافی نیست.** مجتمعی که ساعتی دو پرداخت دارد، با
یک شکست به پنجاه درصد می‌رسد — و آن یک شکست می‌تواند صرفاً کسی باشد که در
صفحه‌ی بانک منصرف شده. هشدارِ هرروزه‌ی بی‌مورد همان چیزی است که باعث
می‌شود روزِ قطعیِ واقعیِ درگاه، کسی هشدار را نخواند.

🔴 **«بلاتکلیف» شکست حساب می‌شود.** از دیدِ ساکن، پرداختی که نتیجه‌اش از
بانک نیامده با ناموفق فرقی ندارد — و از دیدِ اپراتور بدتر است، چون ممکن
است پول کسر شده باشد و ما ندانیم (R59).

**شدت `degraded` است نه `down`:** درگاهِ بانکی که کار نمی‌کند دلیلی برای
پایین‌آوردنِ سایتِ ساکنین نیست.

**وقتی زنگ زد:**

```bash
php artisan payments:stale
```

سپس `docs/DISASTER_RECOVERY.md` سناریوی ⑨ (درگاهِ پرداخت).

### ③ شکستِ پیامک — `sms`

|            |                                                                      |
| ---------- | -------------------------------------------------------------------- |
| **آستانه** | `ALERT_SMS_FAILURE_PERCENT` (۵۰) با کفِ `ALERT_SMS_MIN_ATTEMPTS` (۳) |
| **شدت**    | `degraded` — و **`down` وقتی هیچ ارسالی موفق نبوده**                 |
| **مبنا**   | شمارنده‌های `SmsOutcome` در کش                                       |

🔴 **تنها هشداری که به `down` می‌رسد، و دلیلش:** پیامکِ این سامانه فقط
کدِ ورود است. شکستِ کاملش یعنی **هیچ‌کس نمی‌تواند وارد شود** — در حالی که
سایت بالاست، دیتابیس سالم است، `/up` سبز است و هیچ استثنایی هیچ‌جا ثبت
نشده. این ساکت‌ترین قطعیِ کاملِ این سامانه است.

**نقصی که پیش از R64 وجود داشت:** `SmsManager::send()` یک `bool`
برمی‌گرداند و **هیچ‌جا شمرده نمی‌شد**. تنها ردِ شکست، ستونِ
`sms_campaigns.failed` بود که فقط کارزارِ ماهانه‌ی شارژ را پوشش می‌دهد —
یعنی مسیرِ ورود، که مهم‌ترین است، هیچ ردی نداشت.

⚠️ شمارش در `SmsManager` نشسته، نه در محلِ فراخوانی. چهار جای مختلف پیامک
می‌فرستند و اولین جای پنجم که کسی اضافه کند از قلم می‌افتاد. یک تستِ
ساختاری می‌سنجد که هیچ‌کس درایور را مستقیم نسازد و این لایه را دور نزند.

⚠️ درایورِ `log` همیشه موفق است، پس در توسعه و تست هشدارِ کاذب نمی‌دهد.

**وقتی زنگ زد:** «تنظیمات پیامک» در پنلِ ادمینِ کل → «ارسال آزمایشی». اگر
شکست خورد، معمولاً یکی از این دو است: اعتبارِ پنل تمام شده، یا کلیدِ API
عوض شده.

### ④ شکستِ بکاپ — `backups`

|            |                                                                                |
| ---------- | ------------------------------------------------------------------------------ |
| **آستانه** | هر ردیفِ `failed`؛ `ALERT_BACKUP_PENDING_MINUTES` (۶۰)؛ `BACKUP_RPO_HOURS` + ۱ |
| **شدت**    | `degraded`                                                                     |

🔴 **اندازه‌گیری‌شده پیش از R64:** `BuildBackupJob::failed()` وضعیتِ ردیف
را `failed` می‌کرد و **هیچ‌جای کد آن ستون را نمی‌خواند**. بکاپِ
شکست‌خورده یک ردیفِ قرمز در جدولی بود که کسی نگاهش نمی‌کند.

سه نشانه، چون بکاپ سه‌جور می‌میرد:

| نشانه                               | یعنی                       |
| ----------------------------------- | -------------------------- |
| ردیفِ `failed`                      | کار اجرا شد و ترکید        |
| ردیفِ `pending`ِ کهنه               | ⚠️ **کارگرِ صف اجرا نشده** |
| تازه‌ترین بکاپِ سالم کهنه‌تر از RPO | زمان‌بند اجرا نمی‌شود      |

⚠️ **حالتِ دوم ساکت‌ترین است:** ردیف **پیش از** صف‌شدن ساخته می‌شود، پس
کارگرِ مرده نه خطایی می‌سازد نه ردیفِ قرمزی — ردیف برای همیشه `pending`
می‌ماند.

⚠️ اینجا عمداً هیچ فایلی باز یا رمزگشایی نمی‌شود؛ آن کارِ سنگین مالِ
`backups:verify` هفتگی است. این سنجه فقط شکافِ بینِ دو اجرای هفتگی را
می‌پوشاند.

**و از R64، خودِ `backups:verify` هم از مسیرِ هشدار رد می‌شود.** پیش از
این، خروجی‌اش فقط به **stdoutِ cron** می‌رفت — یعنی «بکاپِ شما قابلِ
بازیابی نیست»، بدترین خبرِ ممکنِ این سامانه، در جایی نوشته می‌شد که
هیچ‌کس نمی‌خواندش.

**وقتی زنگ زد:**

```bash
php artisan backups:verify
```

## 🔒 سه چیزی که از داخلِ PHP سنجیده نمی‌شوند

⚠️ این سه بند در نقشه‌ی ایرادات هستند و **انجام نشده‌اند**. دلیلشان
اینجاست، همراه با کاری که به‌جایش باید کرد. نوشتنِ سنجه‌ای که ادعای
نسنجیده بکند، از نداشتنش بدتر است.

### CPU و Memory

`sys_getloadavg()` بارِ **کلِ ماشین** را می‌دهد.

🔴 روی سرورِ هدفِ این پروژه، nginx مسیرِ دیگری را هم با PHP 7.4 سرو
می‌کند. یعنی عددی که این تابع می‌دهد ممکن است کاملاً مالِ آن یکی برنامه
باشد. هشداری که نمی‌تواند بگوید تقصیرِ کیست، فقط اپراتور را به دنبالِ
نخودِ سیاه می‌فرستد.

و بدتر: PHP-FPM وقتی حافظه تمام می‌کند، **همان پردازه‌ای را می‌کشد که
قرار بود گزارش بدهد**. ابزاری که خودش قربانیِ خرابی است نمی‌تواند گزارشش
کند — همان استدلالی که در R43 برای ضربانِ زمان‌بند نوشته شد.

**به‌جایش:** پایشِ سطحِ سیستم روی خودِ سرور. یک نمونه‌ی کمینه بدون هیچ
وابستگیِ تازه:

```bash
# /etc/cron.d/sakena-load  — هر پنج دقیقه
*/5 * * * * root awk '{ if ($1 > 8) print "load " $1 }' /proc/loadavg | \
  xargs -r -I{} curl -fsS -m 5 -X POST "$ALERT_WEBHOOK_URL" \
  -H 'Content-Type: application/json' -d '{"source":"server","problems":{"load":"{}"}}'
```

عددِ ۸ را با تعدادِ هسته‌های سرور تنظیم کنید (معمولاً ۲ برابرِ هسته‌ها).

### انقضای گواهیِ SSL

گواهی مالِ nginx است و **قیدِ صریحِ این پروژه، دست‌نزدن به پیکربندیِ
nginx است**.

⚠️ می‌شد از داخلِ برنامه به `APP_URL` وصل شد و گواهیِ همتا را خواند، ولی
روی سروری که DNSِ داخلی و بیرونی‌اش یکی نیست، همان اتصال به گره‌ی خودش
نمی‌رسد و هشدارِ کاذبِ روزانه می‌سازد. و اگر گواهی واقعاً منقضی شود،
همان اتصال هم شکست می‌خورد — یعنی سنجه دقیقاً در لحظه‌ای کور می‌شود که
باید ببیند.

**به‌جایش**، روی خودِ سرور:

```bash
# هر روز ساعت ۷ صبح — کمتر از ۱۴ روز مانده به انقضا خبر بده
0 7 * * * root openssl x509 -enddate -noout -checkend 1209600 \
  -in /etc/letsencrypt/live/DOMAIN/fullchain.pem >/dev/null || \
  curl -fsS -m 5 -X POST "$ALERT_WEBHOOK_URL" -H 'Content-Type: application/json' \
  -d '{"source":"server","problems":{"ssl":"گواهی کمتر از ۱۴ روز اعتبار دارد"}}'
```

### و یک چیزِ چهارم: مرگِ خودِ سرور

🔴 هیچ‌کدام از هشدارهای این سند وقتی کار می‌کنند که سرور خاموش باشد —
چون همه‌شان **روی همان سرور** اجرا می‌شوند.

⚠️ این را فقط پایشِ بیرونی می‌گیرد. هر سرویسی که هر چند دقیقه به `/up`
بزند کافی است (UptimeRobot، Better Stack، یا حتی یک cron روی ماشینِ
دیگر). با هدرِ `X-Health-Secret` گزارشِ کامل برمی‌گردد، بدونش فقط وضعیتِ
یک‌کلمه‌ای.

این همان استدلالِ R43 است و با R64 عوض نشده: هیچ ابزاری نمی‌تواند مرگِ
خودش را گزارش کند.

## اجرای دستی

```bash
php artisan alerts:scan     # جدولِ چهار نشانه + اعلامِ هشدارِ تازه
php artisan health:check    # هفت سنجه‌ی زیرساختی (R43)
php artisan backups:verify  # سنجشِ عمیقِ بکاپ (هفتگی، R58)
```

⚠️ هر سه در حالتِ زمان‌بندی‌شده `--quiet-when-ok` می‌گیرند: وقتی چیزی
اعلام نشده، خروجی هم نیست. وگرنه cron هر ربع ساعت یک پیامِ «همه‌چیز خوب
است» می‌ساخت و اپراتور ظرفِ یک هفته یاد می‌گرفت خروجیِ این cron را نخواند
— درست همان عادتی که روزِ خرابی گران تمام می‌شود.
