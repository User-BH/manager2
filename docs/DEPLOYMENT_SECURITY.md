# امنیتِ استقرار — پیشنهادهای سطحِ سرور

> ⚠️ **هیچ‌کدام از این‌ها اعمال نشده است.** طبق قیدِ صاحبِ پروژه، کانفیگِ nginx
> دست‌کاری نمی‌شود؛ سرور مسیرهای دیگری (از جمله یک مسیر با PHP 7.4) را هم سرو
> می‌کند و تغییرِ کانفیگ می‌تواند آن‌ها را بشکند. این سند فقط **پیشنهاد** است تا
> هر وقت مدیرِ سرور صلاح دانست، آگاهانه اعمال کند.

---

## چه چیزی همین حالا کار می‌کند (بدونِ nginx)

هدرهای امنیتی در لایه‌ی لاراول اعمال می‌شوند
([`SecurityHeaders`](../app/Http/Middleware/SecurityHeaders.php)) و با
[`SecurityHeadersTest`](../tests/Feature/SecurityHeadersTest.php) تست دارند.
پس **برای کار کردن، به هیچ تغییری در nginx نیاز نیست**:

| هدر                         | مقدار                             | چه چیزی را می‌گیرد              |
| --------------------------- | --------------------------------- | ------------------------------- |
| `Content-Security-Policy`   | پویا، با nonce                    | تزریقِ اسکریپت (XSS)            |
| `X-Content-Type-Options`    | `nosniff`                         | حدسِ نوعِ فایل توسط مرورگر      |
| `X-Frame-Options`           | `DENY`                            | clickjacking                    |
| `Referrer-Policy`           | `strict-origin-when-cross-origin` | نشتِ آدرسِ صفحه به سایتِ بیرونی |
| `Permissions-Policy`        | دوربین/میکروفن/موقعیت خاموش       | دسترسیِ ناخواسته به سخت‌افزار   |
| `Strict-Transport-Security` | فقط روی HTTPS و بیرون از `local`  | حمله‌ی downgrade به HTTP        |

مزیتِ این‌که در لاراول‌اند: با کد نسخه‌بندی می‌شوند، تست دارند، و با هر استقرار
خودبه‌خود می‌آیند — برخلافِ کانفیگِ سرور که کسی یادش می‌رود.

---

## آنچه لاراول **نمی‌تواند** انجام دهد

سه چیز هست که فقط در سطحِ سرور شدنی است. تا وقتی اعمال نشوند، این‌ها شکاف‌های
باقی‌مانده‌اند — و بهتر است دانسته باقی بمانند تا ناشناخته:

### ۱) هدر روی فایل‌های ایستا

nginx فایل‌های `build/*.js` و `*.css` را مستقیم سرو می‌کند و **اصلاً واردِ PHP
نمی‌شود** — یعنی میان‌افزارِ ما آن‌ها را نمی‌بیند. ریسکش کم است (فایلِ ایستا
اسکریپت اجرا نمی‌کند)، ولی `nosniff` رویشان بی‌فایده نیست:

```nginx
location ~* \.(js|css|woff2|svg|png|jpg|webp)$ {
    add_header X-Content-Type-Options "nosniff" always;
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

### ۲) هدایتِ HTTP به HTTPS

بدونِ آن، اولین درخواستِ کاربر روی HTTP می‌رود و کوکیِ نشست قابلِ شنود است.
HSTS فقط از **دومین** بازدید به بعد محافظت می‌کند:

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
```

### ۳) پنهان‌کردنِ نسخه‌ی سرور

```nginx
server_tokens off;
```

نسخه‌ی دقیقِ nginx به مهاجم می‌گوید دنبالِ کدام آسیب‌پذیریِ شناخته‌شده بگردد.

## دو تنظیمِ `.env` که در محصول لازم است

```dotenv
APP_ENV=production
APP_DEBUG=false
SESSION_SECURE_COOKIE=true
```

`SESSION_SECURE_COOKIE` اگر تنظیم نشود، در `production` خودبه‌خود `true`
می‌شود ([`config/session.php`](../config/session.php)) — عمداً این‌طور نوشته شد
تا فراموش‌کردنِ `.env` به کوکیِ ناامن منجر نشود. ولی صریح نوشتنش بهتر است.

> 🔴 اگر پشتِ پراکسی/CDN هستید و TLS آنجا خاتمه می‌یابد، لاراول درخواست را
> «ناامن» می‌بیند و **HSTS نمی‌فرستد**. در این حالت `TrustProxies` باید
> پیکربندی شود، وگرنه هدر بی‌صدا غایب می‌ماند.

## `'unsafe-inline'` روی استایل — چرا هست و چرا مشکل نیست

`style-src` مجبور است `'unsafe-inline'` داشته باشد: کلِ رابط از
`style={{ ... }}` استفاده می‌کند تا رنگ‌ها از متغیرهای CSS بیایند، و **ویژگیِ
`style` درون‌خطی nonce نمی‌پذیرد** (این محدودیتِ خودِ استاندارد است، نه انتخابِ
ما). تنها راهِ حذفش بازنویسیِ همه‌ی کامپوننت‌هاست.

ریسکش هم بسیار کمتر از `script-src 'unsafe-inline'` است: با CSS می‌شود ظاهر را
خراب کرد، ولی **کد اجرا نمی‌شود**. اسکریپت‌های درون‌خطی — که خطرِ واقعی‌اند —
همگی nonce دارند.
