# خطِ انتشار — شانزده گام، و چه چیزی هرکدام را نگه می‌دارد

> ⚠️ این سند فهرستِ آرزو نیست. هر گام به **جایی در کد** گره خورده، و یک
> تست می‌سنجد که آن جا واقعاً وجود داشته باشد.

## دو نیمه‌ی خط

| نیمه             | کِی اجرا می‌شود   | کجا          |
| ---------------- | ----------------- | ------------ |
| گام‌های ۱ تا ۱۱  | هر push و هر PR   | `ci.yml`     |
| گام‌های ۱۲ تا ۱۶ | فقط با اجرای دستی | `deploy.yml` |

🔴 **استقرار عمداً خودکار نیست.** وصل‌کردنش به `push` یعنی هر merge —
حتی یک اصلاحِ تایپی — مهاجرت روی دیتابیسِ محصول اجرا کند. آن تصمیم مالِ
صاحبِ سامانه است، نه یک قاعده‌ی خودکار.

### ⚠️ گامِ ۸ چرا این شکلی است

CodeQL برای مخزنِ **خصوصی** به GitHub Advanced Security (پولی) نیاز دارد
و در دسترس نیست. پس «اسکنِ امنیتی» اینجا مجموعه‌ای از تست‌های واقعی است:

| تست                       | چه چیزی را می‌گیرد                     |
| ------------------------- | -------------------------------------- |
| `CommittedSecretsTest`    | رازی که واقعاً کامیت شده (تازه در R71) |
| `InjectionSurfaceTest`    | سطحِ تزریق                             |
| `AuthorizationAttackTest` | عبور از مرزِ دسترسی                    |
| `TenantIsolationTest`     | نشتِ داده بینِ مجتمع‌ها                |
| `UploadSecurityTest`      | آپلودِ خطرناک                          |
| `MassAssignmentTest`      | پرکردنِ انبوهِ ستون‌های حساس           |
| `SecretHandlingTest`      | نشتِ راز به لاگ و فرانت                |
| `SecurityHeadersTest`     | هدرهای امنیتی                          |

🔴 **شکافی که `CommittedSecretsTest` بست:** `.gitignore` فایلِ
**ازپیش‌ردیابی‌شده** را از ردیابی خارج نمی‌کند. اگر کسی یک بار `.env` را
کامیت کرده باشد و بعد الگویش را اضافه کند، تستِ قدیمی سبز می‌ماند و راز
همچنان در مخزن است. این تست از **خودِ `git ls-files`** می‌پرسد.

## گام‌های ۱۲ تا ۱۶ — در استقرار

| #   | گام                      | جزئیات                                             |

| ۱۶  | **Smoke Test**           | چهار بررسیِ واقعیِ HTTP (تازه در R71)              |

### 🔴 گامِ ۱۳ — چرا «بکاپ گرفته شد» کافی نیست

`mysqldump` و `tar` می‌توانند با کدِ خروجیِ **صفر** تمام شوند و فایلی
خالی یا نیمه بگذارند: دیسک پر شود، دسترسی نباشد، یا لوله وسط قطع شود.

⚠️ و بدترین حالت همین است: استقرار با خیالِ راحت جلو می‌رود، و وقتی
مهاجرت خراب می‌کند و کسی سراغِ بازگشت می‌رود، تازه معلوم می‌شود فایل صفر
بایتی است.

سه سنجه اجرا می‌شود:

1. فایل وجود دارد
2. بیش از یک کیلوبایت است (فایلِ صفر بایتی هم «وجود دارد»)
3. `gzip -t` بازش می‌کند، و دامپ دستِ‌کم یک `CREATE TABLE` دارد

🔴 دامپی که هیچ جدولی ندارد، دامپ نیست — همان درسِ R58: **بکاپی که
سنجیده نشده، بکاپ نیست.**

### 🔴 گامِ ۱۶ — چرا `/up` تستِ دود نیست

`/up` می‌گوید «زیرساخت سالم است»: دیتابیس، کش، دیسک، صف. هیچ‌کدام ثابت
نمی‌کنند **کاربر چیزی می‌بیند**.

⚠️ استقراری که دارایی‌هایش منتقل نشده، یا `route:cache` را با مسیرِ خراب
ساخته، `/up` را سبز رد می‌کند و صفحه‌ی اصلی سفید است.

| بررسی                      | چه چیزی را ثابت می‌کند                            |
| -------------------------- | ------------------------------------------------- |
| `/` دارای `<title>`        | صفحه‌ی فرود واقعاً رندر می‌شود                    |
| `/` دارای `/build/assets/` | بیلد درست منتقل شده                               |
| `/auth` دارای `<title>`    | مسیرِ ورود بالا می‌آید                            |
| `/api/v1/dashboard` = ۴۰۱  | ⚠️ نه ۵۰۰ (برنامه خراب) و نه ۲۰۰ (محافظت برداشته) |

⚠️ عمداً فقط مسیرهای **عمومی**: تستِ دود نباید نشست بسازد یا داده‌ی
واقعی را دست بزند.

## توقف، بازگشت، و آنچه برنمی‌گردد

| موضوع                | وضعیت                                    |
| -------------------- | ---------------------------------------- |
| توقف در شکستِ هر گام | ✅ هر گام `exit 1` می‌دهد و job می‌ایستد |
| بازگشتِ **کد**       | ✅ خودکار، از همان بکاپِ سنجیده‌شده      |
| بازگشتِ **دیتابیس**  | ⚠️ عمداً دستی                            |

🔴 **چرا دیتابیس خودکار برنمی‌گردد:** هر نوشتنی که در پنجره‌ی استقرار رخ
داده — پرداختِ ساکن، پیامِ تازه، رسیدِ آپلودشده — با بازگرداندنِ دامپ
بی‌صدا پاک می‌شود. آن تصمیم باید با چشمِ باز گرفته شود، نه در دلِ jobی که
کسی نگاهش نمی‌کند. دامپ سرِ جایش می‌ماند و مسیرش در لاگ چاپ می‌شود.

## 🔒 Blue-Green و Rolling — و چرا ساخته نشد

هر دو به چیزی نیاز دارند که این نصب ندارد:

| نیاز                              | وضعیتِ این پروژه                              |
| --------------------------------- | --------------------------------------------- |
| دو محیطِ هم‌زمان                  | یک سرور                                       |
| متعادل‌کننده‌ی بار برای جابه‌جایی | ندارد                                         |
| پیکربندیِ nginx برای سوییچ        | 🔴 قیدِ صریحِ پروژه: به nginx دست زده نمی‌شود |
| چند گره برای Rolling              | یک گره                                        |

⚠️ **و بدونِ آن‌ها چه داریم:** `php artisan down` پیش از مهاجرت و
`php artisan up` پس از آن — یعنی یک پنجره‌ی کوتاهِ «در دستِ تعمیر» با
صفحه‌ی ۵۰۳ فارسی، به‌جای خطای خام.

🔴 **ساختنِ نیمه‌ی Blue-Green روی یک سرور، بدتر از نداشتنش است:** پیچیدگیِ
دو مسیرِ استقرار را می‌آورد بی‌آنکه مزیتِ اصلی‌اش (استقرارِ بدونِ قطعی و
بازگشتِ آنی) را بدهد.

هر وقت سرورِ دوم و متعادل‌کننده اضافه شد، این بند دوباره باز می‌شود.
