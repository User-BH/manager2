# استقرار: کانتینرِ اختیاری و پیشنهادهای سرورِ فعلی

> ⚠️ **این سند چیزی را روی سرورِ شما عوض نمی‌کند.**
>
> قیدِ شما صریح بود: کانفیگِ nginxِ موجود دست‌کاری نشود، MySQL و
> phpMyAdminِ نصب‌شده دست‌نخورده بمانند، و مسیرِ PHP 7.4 آسیب نبیند.
> بخشِ اول این سند یک محیطِ **کاملاً جدا** را توضیح می‌دهد، و بخشِ دوم
> پیشنهادهایی است که **شما** تصمیم می‌گیرید اعمال شوند یا نه.

---

## بخش ۱ — محیطِ کانتینری (جدا و اختیاری)

### چه چیزی ساخته شد

| سرویس      | تصویر                      | نقش                        | پورتِ میزبان  |
| ---------- | -------------------------- | -------------------------- | ------------- |
| `app`      | ساختِ خودمان (PHP 8.4-FPM) | برنامه                     | — (فقط داخلی) |
| `web`      | `nginx:1.27-alpine`        | وب‌سرور                    | **۸۰۸۰**      |
| `worker`   | همان تصویرِ `app`          | صف + زمان‌بند (supervisor) | —             |
| `database` | `mysql:8.4`                | دیتابیسِ **مستقل**         | **۳۳۰۶۱**     |
| `cache`    | `redis:7-alpine`           | کش، نشست، صف               | **۶۳۷۹۱**     |

### چرا با سرورِ فعلی تصادم نمی‌کند

⚠️ سه محافظ، و هر سه عمدی:

1. **پورت‌های غیرِ استاندارد.** ۸۰۸۰ / ۳۳۰۶۱ / ۶۳۷۹۱ به‌جای ۸۰ / ۳۳۰۶ /
   ۶۳۷۹. حتی اگر nginx و MySQL و Redisِ خودِ سرور بدوند، هیچ‌کدام گرفته
   نیست.
2. **فقط روی `127.0.0.1`.** هر سه پورت با پیشوندِ `127.0.0.1:` منتشر
   شده‌اند. بدونِ آن، Docker قاعده‌ی iptables می‌سازد که **فایروالِ میزبان
   را دور می‌زند** و سرویس روی اینترنت باز می‌شود بی‌آنکه کسی خواسته
   باشد.
3. **دیتابیسِ جدا.** کانتینرِ MySQL دیتابیسِ خودش را در volumeِ خودش
   می‌سازد و به داده‌ی موجود دست نمی‌زند.

### اجرا

```bash
cp .env.docker.example .env.docker
# APP_KEY و رمزها را پر کنید
docker compose --env-file .env.docker up -d --build
```

کلیدِ برنامه:

```bash
docker compose run --rm app php artisan key:generate --show
```

### تصمیم‌هایی که ارزشِ توضیح دارند

**چرا Dockerfile چندمرحله‌ای است.** Composer و Node فقط برای **ساخت**
لازم‌اند. اگر در تصویرِ نهایی بمانند، حدودِ ۴۰۰ مگابایت ابزارِ ساخت روی هر
سرورِ محصول می‌نشیند که هرگز اجرا نمی‌شود — و هر کدام سطحِ حمله‌ی خودش را
دارد.

**چرا `gd` با freetype ساخته می‌شود.** mPDF فونتِ فارسی را با freetype
رندر می‌کند و دستورِ `pwa:splash` تصاویر را با همان می‌سازد. `gd`ِ ساده هر
دو را **بی‌صدا** خراب می‌کند: نه خطایی می‌دهد نه لاگی، فقط خروجی غلط
می‌شود.

**چرا `pm.max_requests = 500`.** اندازه‌گیریِ R28 نشان داد mPDF حدودِ ۳۰
مگابایت را دائمی نگه می‌دارد. بدونِ بازیافتِ پردازه، همان پردازه‌ای که چند
PDF ساخته صدها مگابایت را تا ابد نگه می‌دارد.

**چرا Redis با `noeviction`.** این Redis هم کش است هم **صف**. با
`allkeys-lru`، زیرِ فشارِ حافظه کارهای صف هم دور ریخته می‌شوند — یعنی قبضی
صادر نشده یا پیامکی نرفته و هیچ‌کس نمی‌فهمد. `noeviction` به‌جایش خطا
می‌دهد، که دیده می‌شود.

**چرا `schedule:work` و نه cron.** در کانتینر، cron یک دیمنِ دومی است که
باید خودش زنده نگه داشته شود و لاگش جای دیگری می‌رود. `schedule:work` یک
پردازه‌ی معمولی است که supervisor می‌پایدش و لاگش به `docker logs` می‌رسد.

**چرا `mysqladmin ping` برای سلامت و نه بررسیِ پورت.** پورتِ ۳۳۰۶ خیلی
زودتر از آماده‌شدنِ موتور باز می‌شود؛ با بررسیِ پورت، کانتینرِ برنامه
زودهنگام شروع می‌کند و اولین `migrate` با «Connection refused» می‌افتد.

## بخش ۲ — پیشنهادها برای سرورِ فعلی

> ⚠️ **هیچ‌کدام از این‌ها اعمال نشده.** متن است، نه تغییر. اگر خواستید،
> خودتان اعمالشان کنید — و پیش از هر تغییری از کانفیگ نسخه‌ی پشتیبان
> بگیرید.

### ۲.۱ آنچه **از قبل درست است** (سنجیده شد)

اندازه‌گیریِ R38 روی خودِ `sakena.ir` نشان داد:

```
Content-Encoding: gzip
Cache-Control: max-age=31536000, public, immutable
```

یعنی **فشرده‌سازی و کشِ دارایی‌ها از قبل برقرارند** (از طریقِ ArvanCloud).
اینجا کاری لازم نیست.

### ۲.۲ آنچه شاید بخواهید اضافه کنید

**① `sw.js` نباید کش شود.**

⚠️ مهم‌ترین موردِ این فهرست. اگر مرورگر نسخه‌ی کهنه‌ی `sw.js` را نگه دارد،
کاربر در نسخه‌ی قدیمِ **کلِ برنامه** گیر می‌کند — چون همان فایل تصمیم
می‌گیرد چه چیزی از کش بیاید. این تنها فایلی است که کش‌شدنش می‌تواند
به‌روزرسانی را برای همیشه ببندد.

```nginx
location = /sw.js {
    add_header Cache-Control "no-cache, no-store, must-revalidate" always;
    expires off;
}
```

**② سقفِ آپلود هماهنگ با برنامه.**

سقفِ برنامه ۴ مگابایت است. اگر `client_max_body_size` کمتر باشد، کاربر
به‌جای پیامِ فارسیِ ما خطای ۴۱۳ی خامِ nginx را می‌بیند.

```nginx
client_max_body_size 10M;
```

**③ مهلتِ FastCGI برای خروجی‌های سنگین.**

ساختِ PDFِ دسته‌ای و خروجیِ Excel از صف می‌روند، ولی دانلودشان می‌تواند
طول بکشد.

```nginx
fastcgi_read_timeout 120s;
```

**④ `memory_limit` برای PHP-FPM و کارگرِ صف.**

⚠️ این یکی **الزام است، نه پیشنهاد**. R28 اندازه گرفت که ساختِ PDFِ
دسته‌ای روی ۱۲۸ مگابایت با «Allowed memory size exhausted» می‌افتد:

```ini
memory_limit = 256M
```

**⑤ بازیافتِ پردازه.**

```ini
pm.max_requests = 500
```

دلیلش همان نشتِ حافظه‌ی mPDF است که بالا توضیح داده شد.

**⑥ Brotli کنارِ gzip.**

سودش حدودِ ۱۵–۲۰٪ نسبت به gzip است. تنظیمش روی ArvanCloud/nginx در اختیارِ
شماست.

### ۲.۳ چیزی که **نباید** عوض شود

- **`.env` و درایورها.** برنامه روی سرورِ فعلی با `database` برای صف و کش
  و نشست کار می‌کند و درست کار می‌کند. تصمیمِ Redis مالِ محیطِ کانتینری
  است؛ بردنش به سرورِ فعلی یعنی وابستگیِ تازه‌ای که باید نصب و پایش شود.
- **مسیرِ PHP 7.4.** کانتینر PHP 8.4ِ خودش را دارد و به PHPِ نصب‌شده‌ی
  میزبان کاری ندارد.

## چه چیزی آزموده شد و چه چیزی نه

✅ **آزموده شد:** ساختارِ `compose.yaml` با `docker compose config`
اعتبارسنجی شد و هر سه پورتِ منتشرشده روی `127.0.0.1` تأیید شدند. تستِ
`DockerEnvironmentTest` قیدها را قفل کرده.

⚠️ **آزموده نشد:** ساخت و اجرای واقعیِ کانتینرها. daemonِ Docker روی این
ماشین بالا نبود (`docker info` با «cannot find the file specified» شکست
خورد)، پس `docker compose up` اجرا نشد. تصویرها هرگز ساخته نشده‌اند و
اولین اجرا ممکن است به اصلاحاتی نیاز داشته باشد — به‌ویژه در نصبِ
افزونه‌های PHP که به نسخه‌ی دقیقِ Alpine حساس است.
